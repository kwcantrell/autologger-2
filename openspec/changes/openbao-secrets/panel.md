# Panel: openbao-secrets
Tier: 2 · Reviewers: assumption tester, failure and abuse, scope and simplicity · Date: 2026-10-03

- [x] [major] Stack AppRole policy grants `read` on `database/creds/<env>-*` (incl. `<env>-admin`) that nothing uses; a stolen `.env.openbao.<env>` (or any process on the bound VM, which shares its /32) can mint admin Postgres users. Evidence: docs/openbao-secrets.md AppRole table "plus `read` on `database/creds/<env>-*`"; compose-run.mjs:384-396 only calls login, KV read, revoke-self; bao-psql.sh:158 uses the operator session. (scope + failure/abuse) Resolved: database-engine feature cut to a follow-up (owner, 2026-10-03); stack AppRole policy is `read` on `kv/data/autologger/<env>` only (docs/openbao-secrets.md, docs/security.md, local-container-environments delta, task 1.3, ADR 0025); spark-infra 4c345b6 applies the same policy live.
- [x] [major] The `bao-db` overlay breaks db's host isolation: joining a non-internal network gives db a default route to the VM host (sshd etc. reachable) and gives the host an address on `bao-db`, so host processes reach 5432 directly, bypassing the planned DOCKER-USER rule; contradicts D4 and the container-deployment "no host process SHALL connect" clause; invariant 17 misses it. Evidence: throwaway replica `cat /proc/net/route` -> `eth1 00000000 010016AC` (default route), `nc -z 172.22.0.1 22` -> OPEN, host `psql -h 172.21.0.2` -> connected. (assumption tester) Resolved: docker/compose.bao-db.yaml, the bao-db network and its compose-env.sh inclusion are deleted; db stays only on the internal `db` and `catalog` networks as on supabase-migration; the follow-up must ship with no host route for db (proposal Non-goal).
- [x] [major] The database-engine connection is plaintext (`ssl = off` in the supabase image) across the shared lxdbr0 bridge, protected only by an out-of-repo, unverified source-IP rule; a co-tenant VM can spoof 10.88.0.10 and relay the engine's root SCRAM login, or reach every role if the rule is absent. Evidence: `grep -n '^ssl' /etc/postgresql/postgresql.conf` -> `105:ssl = off`; pg_hba `host all all 10.0.0.0/8 scram-sha-256`. (failure/abuse) Resolved: no database-engine connection in this change; the follow-up must add Postgres TLS (verify-full, internal CA) first (proposal and design Non-goals); spark-infra 4c345b6 removed the `database/` mount.
- [x] [major] `BAO_DB_BIND` and the overlay are enabled for prod although nothing in this change uses them (Non-goals exclude `prod-psql`), opening a new network path to prod Postgres. Evidence: compose-run.mjs:36 `prod: [..., 'BAO_DB_BIND', ...]`; compose-env.sh adds the overlay in `compose_prod`. (scope) Resolved: `BAO_DB_BIND` removed from every env's compose keys, the `resolved` guard and compose-env.sh (dev, stage, prod); a new test asserts no env allows any `BAO_*` name; the follow-up is dev/stage only.
- [x] [major] container-deployment delta contradicts itself: the Host exposure clause lets db join `bao-db`, but the unchanged Network segmentation clause in the same MODIFIED requirement still says db is only on `db` and `catalog`; scenario titles still say Infisical (renaming inside a MODIFIED block is allowed). Evidence: specs/container-deployment/spec.md lines 11-20 vs 21-28, line 92. (scope) Resolved: bao-db exception and `BAO_DB_BIND` wording removed from both deltas (strict validate passes); the two Infisical scenario titles stay because OpenSpec 1.13.2 rejects dropping a current scenario name in a MODIFIED block; their bodies say OpenBao and the tasks.md "Owner-owed after merge" step renames them in openspec/specs/ after archive.
- [x] [major] `supabase-keys.mjs` regenerates every database/JWT secret and drops all other keys when the current KV version is soft-deleted (404 with metadata), breaking "an existing key is never overwritten"; the guard checks `metadata.deleted_time` but KV v2's field is `deletion_time` (same dead check in compose-run.mjs:152). Evidence: dev server, DELETE then re-run -> `created POSTGRES_PASSWORD ... created SERVICE_ROLE_KEY`, rc=0, no `kept`. (failure/abuse + assumption tester) Resolved: compose-run.mjs and supabase-keys.mjs use KV v2 `deletion_time` and `destroyed` (shared isDeletedVersion) and refuse a soft-deleted or destroyed current version, naming `bao kv undelete`/`rollback`; tests written first and seen failing (supabase-keys 5 cases, compose-run unit + end-to-end); tasks 3.5, 4.4.
- [x] [major] Accepted ADR 0021 still records "Secrets live in a shared Infisical instance"; the change reverses it with no superseding ADR. Evidence: `grep -n Infisical docs/decisions/0021-*.md` -> lines 69, 85, 87, 220, 332, 352, 398; `git diff --stat -- docs/decisions` empty. (scope) Resolved: ADR 0025 "Stack secrets move from Infisical to OpenBao" supersedes ADR 0021's Infisical clause (owner decision 2026-10-03); 0021's body unchanged per the partial-supersession convention (0022/0018).
- [x] [major] Lifecycle order inverted: approval recorded before this panel, implementation written before the artifacts-first commit, no task ticked with Evidence, and task 2.2's test (exported `BAO_DB_BIND` still passes invariant 16) is missing. Evidence: no `panel.md` before 2026-10-03; `git log -1` = e4e36e1; `grep -n 'BAO_DB_BIND=' docker/scripts/test_check_envs.sh` -> none. (scope) Resolved: re-panel recorded (## Re-panel), owner re-approved the reduced scope in proposal.md, first branch commit c6f21c3 holds only openspec/changes/openbao-secrets/ (artifacts-first gate), every task in tasks.md ticked with Evidence; old task 2.2 no longer applies (BAO_DB_BIND cut).
