# Panel: closed-signups
Tier: 2 · Reviewers: assumption tester, failure and abuse, scope and simplicity · Date: 2026-10-15

No critical findings. Reviewers report only critical and major findings (ADR 0024).

- [x] [major] The change alters team-management's "Email invites" (an invited email's first sign-in no longer always creates the account and materializes the invite) with no delta. Found by scope and simplicity. Evidence: `openspec/specs/team-management/spec.md:37-41` and scenario "Invite before first sign-in". Resolved: MODIFIED "Email invites" in `specs/team-management/spec.md` (materialize only on a sign-in that creates an account; new scenario "An invite does not open closed sign-ups"), listed under Capabilities; covered by task 3.1's first case.
- [x] [major] "Concurrent first sign-in succeeds" still says both callbacks always sign in, contradicting the closed refusal; and design D3 described the race with READ COMMITTED row-lock semantics, while catalog transactions are SERIALIZABLE and re-run on `40001`. The planned "extend the existing test" would not exercise the race (its hold is on the subject lookup, so A takes the existing-account path). Found by scope and simplicity and by the assumption tester. Evidence: `api-contract-freeze/spec.md:1410-1421`; `grep -n "BEGIN ISOLATION\|40001" packages/storage/src/postgresCatalogStore.ts` -> `BEGIN ISOLATION LEVEL SERIALIZABLE`, `new Set(['40001', '40P01'])`; `auth.int.test.ts:682-716` holds on `SELECT * FROM users WHERE google_sub`. Resolved: MODIFIED "Concurrent first sign-in succeeds" (only subjects allowed to create an account; closed and unapproved both get `signup_closed`; new approved scenario); D3 rewritten for SERIALIZABLE (user insert first, consume second, rollback sentinel, log outside the body); task 3.1 names a new concurrent test with its hold point and `RetryCountingRoot`, plus a closed-unapproved concurrent case.
- [x] [major] The `SIGNUPS` boot refusal and boot log line were in the design only, with no spec scenario behind the bootGuard test. Found by scope and simplicity. Evidence: `web-frontend-platform/spec.md:239-259` lists boot refusals; the delta had none. Resolved: both are in the ADDED "Closed sign-up redirect" (following the `PROVIDER_KEYS_SECRET` precedent), with scenarios "A mistyped setting refuses to start" and "The default follows the stack"; task 2.1 tests both.
- [x] [major] A `SIGNUPS` typo was caught only by the server at boot, so `make prod-up` would replace a working `api` with a crash-looping one. Found by failure and abuse. Evidence: `docker/scripts/compose-run.mjs:228-238` (`checkSignInClient` refuses `BOOTSTRAP_OWNER_EMAIL` problems before compose for this reason); `restart: unless-stopped` in `compose.yaml`. Resolved: D1 adds `checkSignupsSetting` in compose-run beside `checkSignInClient` (the bootGuard check stays as a second layer); spec scenario and task 2.1 compose-run test.
- [x] [major] "Only `postgres` may approve" was not enforced: the catalog's default privileges give `catalog_system` insert and update, so any system-bound app path could write an approval. Found by failure and abuse. Evidence: `supabase/migrations/20261001000000_catalog_schema.sql:163`; `pg_default_acl` -> `{catalog_user=arwd,catalog_system=arwd}`. Resolved: the migration revokes `insert, update, truncate` from `catalog_system` (select and delete kept for the callback); catalog-database delta and task 1.1 test both.
- [x] [major] A refused sign-in left a Supabase Auth record (email, name, avatar) with no purge path, and that record could permanently block a later approved Google account with the same email (`identity_unavailable` from GoTrue's email linking). Found by failure and abuse. Evidence: `docker/supabase-services.yaml:44` `GOTRUE_DISABLE_SIGNUP: "false"`; `server/src/auth/gotrue.ts:20,49-54`. Resolved: (owner, 2026-10-15) the closed check runs read-only before the Supabase Auth exchange, so a refused person never reaches it; MODIFIED "OAuth callback failure redirect" amends "Before any account is read or created" to "created or changed" plus the pre-check sentence; only the narrow revoke-during-sign-in race still reaches Supabase Auth (D3).
- [x] [major] An approval was a standing bearer grant with no expiry, usable by any Google account asserting that verified email (non-Gmail addresses stay verified after the mailbox is lost). Found by failure and abuse. Evidence: design D2 had `approved_at_utc` but nothing read it; `auth.ts:178` matches on `email_verified === true` only. Resolved: (owner, 2026-10-15) approvals are usable for 7 days, checked in the pre-check and the consume against the server's Clock; README advises approving shortly before sending the link; scenario "An expired approval is refused" and task 3.1 test.
- [x] [major] "After merge" said to approve stage testers before the deploy, but the approvals table and functions only exist once that deploy's migrate step runs. Found by the assumption tester. Evidence: `docker/supabase-db.yaml` `migrate` runs as part of stack up; `pg_proc` on dev lists no `approve_account`. Resolved: proposal "After merge" and design Risks say to approve right after the deploy.
- [x] [major] The rollback was incomplete: reverted code's compose wrapper refuses a KV secret holding the then-unknown `SIGNUPS` key. Found by the assumption tester. Evidence: `docker/scripts/compose-run.mjs:183-216` (`bad(k, 'not-allowed')` then refuse). Resolved: design Risks and the migration header list "remove `SIGNUPS` from every KV secret" as rollback step 1; V.2 removes it on dev before the VM runs a branch without this change.
