# Panel: ci-db-test-selection
Tier: 2 · Reviewers: assumption tester, failure and abuse, scope and simplicity · Date: 2026-10-07

- [x] [critical] The D4 post-merge run fails on every push to `supabase-migration` before any test runs. A push has no `GITHUB_BASE_REF`, so `resolve_base` falls back to `origin/main` (486 commits behind). The commit stage's `change` check then fails with "one change per branch" (43 archive dirs), and under bash `-e` the full suite never starts, leaving the branch permanently red. Raised by all three reviewers. Evidence: at `origin/supabase-migration` 415cca6b, `env -u GITHUB_BASE_REF CI=1 GITHUB_EVENT_NAME=push scripts/check-change.sh --stage commit` -> `FAIL  change  one change per branch; found ['openspec/changes/archive/2026-09-30-infisical-secrets', ...]`, `SKIP risk-floor blocked: change failed`, exit=1. Resolved: a push to `supabase-migration` runs only `FULL_TESTS=1 scripts/check-change.sh --only commands,audit`, and a push to `main` keeps `--stage commit` (proposal What Changes, design D4 with the `github.event.before` alternative). New task 3.2 simulates the push run before merge. A local check shows a push env with `--only` runs non-change gates: `CI=1 GITHUB_EVENT_NAME=push scripts/check-change.sh --only guide-size,workflows` -> both PASS, rc=0.
- [x] [major] The proposal and design disagree on when selection applies. The proposal said "locally at the `hook` and `pr` stages", while D3 has no stage condition, and `--only` runs get `ctx.stage == "custom"`. Tasks 2.2/2.3 use `--only commands`. Raised by assumption tester and scope reviewer. Resolved: one rule, no stage condition (`--stage hook`, `--stage pr` and `--only commands` select alike). Stated in proposal What Changes and design D3 condition 2.
- [x] [major] The design's mitigation "the gate message shows the skip" doesn't hold locally. Pre-push and the Stop hook call the checker with `--quiet`, which prints failures only. Evidence: `.pre-commit-config.yaml` `entry: scripts/check-change.sh --stage hook --quiet`; `check_change.py` `if not args.quiet or status == "FAIL" or (status == "WARN" and name == "yaml")`. Resolved: D3 now prints the `commands` line under `--quiet` whenever it skipped DB tests. Pre-push already has `verbose: true`, so a passing push shows it. Task 2.2 adds a `--stage hook --quiet` check.
- [x] [major] The time saving isn't measured before approval. The Assumptions table still has the `TIMING` placeholder, and the 509s isn't split between pg/integration and typecheck/unit/audit. Raised by the scope reviewer. Evidence: design.md Assumptions last row; `find server/src -name '*.int.test.ts' | wc -l` -> 89; `*.pg.test.ts` -> 12 in server, 3 in storage. Resolved: measured locally and recorded in the design.md Assumptions table. The pg and integration projects took 597s against 96s for server/storage unit, web and typecheck combined, so skipping them removes most of the test time on a skipped PR. CI hardware differs, and task 3.4 records the CI before/after.

## Re-panel 2026-10-07 (sharding)
Delta: D5 adds a 3-way `db-shard` matrix job and a `db-tests` result job, a `--db-selection` flag, and `DB_TESTS_IN_SHARDS=1` in `gates`. Covers tasks 2.4, 2.5, 3.2-3.5, 4.2 and 4.3.
- [x] [major] `db-tests` (`if: always()`, requires every shard `success`) goes red on every push to `main`, where `db-shard` is skipped by its `if` and its result is `skipped`. It also goes red in every run cancelled by `cancel-in-progress` (new pushes, label or description edits). Raised by all three reviewers. Evidence: delta D5 bullets; `.github/workflows/lifecycle.yml:6-17` (`push: branches: [main]`, PR types include `edited, labeled, unlabeled`, `cancel-in-progress: true`). Resolved: `db-tests` uses `db-shard`'s event condition with `!cancelled()` (design D5). Task 3.2 checks the `if`.
- [x] [major] The required check stops covering the DB tests, and nothing tracks the fix. `main-protect` targets `refs/heads/main` only and requires `gates`, `secrets` and `dependency-review`, and the delta took the DB tests out of `gates`. `docs/security.md:25` and the workflow header still list the old checks. Raised by all three reviewers. Evidence: `gh api repos/:owner/:repo/rulesets/19850235` -> `"include":["refs/heads/main"]`, required `gates, secrets, dependency-review`. Resolved: task 4.2 updates `docs/security.md` and the workflow header. Task 4.3 is the owner's ruleset edit, ticked with `gh api` evidence before archive. The design's risk text now says the protection applies to `main` only (Risks, Migration Plan).
- [x] [major] Sharding `packages/storage` pg (3 files) breaks when the shard count exceeds 3 or the file count drops. Vitest exits 1 when the shard count exceeds the file count, which contradicts the design's "more shards" rebalancing path. Raised by all three reviewers. Evidence: `cd packages/storage && npx vitest run --project unit --shard=4/4` -> `Error: --shard <count> must be a smaller than count of test files. Resolved 3 test files`, exit 1; `find packages/storage/src -name '*.pg.test.ts' | wc -l` -> 3. Resolved: storage pg runs unsharded on shard 1 only (about 51s locally), so the shard count is bounded only by the server's 101 files. `--passWithNoTests` was rejected because it would hide a glob that matches nothing (design D5, tasks 3.2).
- [x] [major] The shard step's parse of `--db-selection` isn't specified to fail toward running. Empty or unexpected output, or a crash, could skip the tests and leave `db-tests` green with zero DB tests run. `main()` prints gate lines before anything else. Raised by failure and abuse and assumption tester. Evidence: delta D5 ("On `skip`, the remaining steps are skipped", no other case); `check_change.py:24-26` (PyYAML `sys.exit`), `:577-604` (main prints the change result first). Resolved: D5 now says the step skips only on exit 0 with exactly one line starting `skip: `. Anything else runs, a non-zero exit fails the shard, and `--db-selection` returns before change resolution or any gate output. Task 2.4 checks one-line stdout, and task 3.2 runs the step's shell against empty, garbage, two-line, `run:` and exit-1 inputs.
- [x] [major] Text from before the delta still said `gates` runs the full DB suite in CI: proposal checker and push bullets, D3 "Otherwise it runs the full suite", the Goals' "says so in the gate output", and task 3.1's push command without `DB_TESTS_IN_SHARDS`. Raised by scope and simplicity. Evidence: proposal.md:24-38, design.md D3 and Goals, tasks.md 3.1. Resolved: the proposal bullets and D3 now say the DB tests run in `db-shard` in CI. The Goals name the `--db-selection` line as the CI output. Task 3.1's push command adds `DB_TESTS_IN_SHARDS=1`.
