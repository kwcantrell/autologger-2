# Panel: batch-autogenerate
Tier: 2 · Reviewers: assumption tester, failure and abuse, scope and simplicity · Date: 2026-11-09

- [x] [critical] Resuming a topics step after a crash leaves the interrupted run's partial topics in place and records them as `present`, which contradicts the spec scenario "Server restart during the topics step … topics step re-runs". `create_topic` inserts each topic per tool call with no run id; D7 counts topics as missing only when `listTopics().length === 0`, and D11 re-runs that check on re-entry. The resulting partial set, which never passed the coverage gate, is permanent and later jobs skip it too. Evidence: `grep -n "insertTopic" packages/ai-runtime/src/aiMcpServer.ts` -> per-call insert, untagged; design.md:272 `topics: missing when listTopics().length === 0`. (Failure reviewer critical; assumption tester major.) Resolved: owner-chosen item-side tracking, no tag column (a tag would change the frozen topic row shape and need a backfill decision): `create_topic` takes a per-turn id allocator that writes each id to the item's new `own_topic_ids` before `insertTopic` inserts with it; re-entry deletes those topics first, then checks missing; own topics never count as present (design D7 topics, D11, R6; batch spec "Steps run…" own-output paragraph and the topics-resume scenario; tasks 3.4, 4.3 kill-mid-turn test).
- [x] [major] Resuming an events step can lose events. A resumed run is a normal run, so the model is shown the interrupted run's partial events as existing and won't recreate them; the worker then deletes them after success. Separately, on a failed or `failed interrupted` ending, events from earlier run ids are never cleaned up. They keep `auto_generated: true`, so `hasAutoGeneratedEvents` marks the session present for good. Evidence: `sed -n 536,560p server/src/routers/events.ts` -> `regenerateSnapshotIds` applies only in regenerate mode; design.md:266-269 cleans up earlier run ids only on success. Resolved: re-entry passes the earlier attempts' event ids through the regenerate-snapshot exclusion (prompt and anchors); success deletes every earlier run id's events; any failed ending, `interrupted` included, deletes the events of every run id in `run_ids` (design D7 events; batch spec own-output and failure paragraphs; tasks 3.3, 4.3).
- [x] [major] A failed batch topics turn deletes topics a person added during the turn, because the run's topics are computed as `after − preRunIds`. In an unattended batch, people keep editing. Identify the run's own topics by the ids its tool created. Evidence: `sed -n 336,366p server/src/routers/transcribe.ts` -> `newIds = after.filter((t) => !preRunIds.has(t.id))` … `hub.deleteTopics(newIds)`. Resolved: the shared runner identifies the run's topics by the ids its tool created, for both the manual route and the batch; spec-identical because topic-generation already says failure deletes "the topics this run created" (A20); the one observable difference (a person's concurrent topic survives a failing manual run) is recorded as R12 and in the proposal's non-goals (design D7 topics, A19-A20; batch spec scenario "A person's topic survives…"; task 3.4).
- [x] [major] Nothing stops the job on persistent provider failure. A revoked or over-quota key, or a 429/5xx storm, fails all 1000 sessions one by one: each transcodes and uploads its audio, and partial multi-group work is paid for and discarded. Only a missing credential row stops the job. Add a job-level stop after N consecutive provider or generation failures, and back off on 429. Evidence: `sed -n 214,217p packages/transcription/src/generateTranscript.ts` -> every `DeepgramUpstreamError` becomes `upstream`; `grep -n "consecutive\|backoff" design.md spec.md` -> none. Resolved: new design D17 — bounded 429 backoff (30/60/120/240/480 s, cancel-aware, then `failed rate-limited`) and a job stop `provider-failing` after 3 consecutive sessions failing with provider/generation/rate-limit outcomes (count on the job row, reset by a `done` step); Deepgram error gains a numeric status (A21); new outcome `rate-limited` and stop reason `provider-failing` in the contract tables and D1 checks; batch spec requirement "Persistent provider failure stops the job"; tasks 3.2-3.4, 4.1, 4.6.
- [x] [major] `autogenerate_jobs.team_id references catalog.studio_definitions (id)` has no `on delete`. Combined with keeping jobs forever, `adminDeleteStudio` (self-serve and admin plane) and the legacy importer's `--replace`/`--replace-live` then fail with 23503 for any team that ever ran a job. Every other per-team or per-user child table cascades. Evidence: `sed -n 276,292p packages/catalog/src/studioRegistry.ts`; `grep -n "DELETE FROM catalog.studio_definitions" server/scripts/legacyImportSql.ts` -> `577`; tasks 1.4 says the importer never touches the new tables. Resolved: `team_id … on delete cascade` (D1). A team with a live job always has shows and no route deletes a show (A22), so `adminDeleteStudio` already refuses with its existing 400 — no change, no contract delta; finished jobs cascade. The legacy importer's `--replace`/`--replace-live` refuse while a job is queued/running (`legacy import refused: team % has a batch autogenerate job in progress; cancel it first`), with the jobs table added to its lock (D1, R11; batch spec "Jobs go with their team"; tasks 1.2 cascade, 1.4 importer, 1.5 team delete, 4.5 vanished-job stop).
- [x] [major] Auto-accept lets injected or hallucinated rewrites silently remove human-written wiki content at scale. `propose_page` replaces the whole body, title and aliases of any page in the show (up to 20 per run). Quote checks cover citations only. `base_revision` protects only against later edits, not against the proposal's own deletions. Over 1000 sessions, plus wiki re-runs (R3), batch revisions stack, so reverting one means discarding every later one. Evidence: `packages/ai-runtime/src/wikiTools.ts:509,519` "The WHOLE new page body"; `:49 WIKI_RUN_MAX_TARGETS = 20`. Owner decision needed on the mitigation (keeps decision 8). Resolved: owner decision 8a (2026-11-09): `accept` mode auto-accepts only new pages and additions-only rewrites — title unchanged after trim, every old alias kept, old body lines (CRLF→LF) a byte-exact in-order subsequence of the new lines; any changed or dropped line, title or alias stays pending; counts accepted vs left pending (proposal 8a; design D12, R1, Q10; show-wiki delta definition and line-rule scenario; batch spec wiki requirement; web-ui confirm copy; tasks 1.1 ADR, 2.3 `isSafeSuggestion` unit test, 4.7).
- [x] [major] The worker deletes events through the system reason `session-undo`, which the core-ports delta still defines as "a request's undo steps, which remove only what that same request wrote". - [x] [major] `provider-failing` never fires for a revoked or over-quota LLM key while speech-to-text works: each transcript `done` resets the counter, so the job pays for transcription and fails 3 LLM turns on every session. - [x] [major] The write-ahead guarantee for `own_topic_ids` and run ids doesn't say what happens when the fenced item write changes 0 rows (lease lost). Resolved: the run-id and topic-id appends are fenced on the job lease; 0 rows means no insert: an events run does not start, `create_topic` refuses that call and latches so the rest of the turn refuses, the turn ends failed and the worker writes nothing more (batch spec "Recording is refused when the job lost its lease"; design D7 "Fenced write-ahead"; tasks 2.4, 3.3, 3.4, 4.3 lease-takeover test).
