# Design: batch-autogenerate

## Context

See proposal.md for the why and the owner decisions (1-8), which are fixed.

Today each generation is a synchronous request on one session, with a guard ladder that the
routes share (`server/src/routers/transcribe.ts`, `events.ts`, `wikiSuggestions.ts`):

| Step | Route | Ladder after the masked session `404` | Single-flight | Writes |
| --- | --- | --- | --- | --- |
| transcript | `POST …/transcript-words/generate` | caller's STT credential `503` → approved-user `403` | in-process `transcriptGenerationLock` + `transcript-generation` run lease | replaces all words atomically in one hub transaction |
| events | `POST …/events/generate` | body `400` → AI route `503` → `403` → no words / no anchors / no instructions / instruction bound `400` | shared `aiChatTurns` slot + `ai-turn` lease | appends events tagged `auto_generated` + `auto_generate_run_id`; on failure the events already inserted **persist** |
| topics | `POST …/topics/generate` | AI route `503` → `403` → no words `400` | same slot + lease | creates new topics, deletes the pre-run topics only on success, deletes its own on failure |
| wiki | `POST …/wiki/generate` | AI route `503` → `403` → no words `400` | same slot + lease | stores `pending` suggestions (tagged `run_id`) in one transaction, only on success |

Every route runs as the signed-in user: `c.get('catalog')` is `sys.forUser(user.id)` and hub
calls go through `userCaller(user.id)`; provider credentials are resolved per request from the
user id (`resolveSttCredential`, `resolveLlmRoute`). Two background precedents exist:

- **The log-import job** (`server/src/routers/logImport.ts`) outlives its request, runs its hub
  calls as its creator (`userCaller(job.createdByUserId)`), resolves the creator's STT credential
  for transcripts, and re-checks `authCanAccessShow(creator, show)` before each sheet. Its state is
  a kv record with a heartbeat; it does **not** resume after a restart.
- **The media job queue** (migration `20261023000000_media_jobs.sql`, ADR 0032) is durable:
  rows claimed with `FOR UPDATE SKIP LOCKED` under a lease, renewed while working, retried when the
  lease lapses, every statement fenced on `locked_by`, a payload-free `NOTIFY` wake-up, and an
  apply loop in the API process (`server/src/mediaApply.ts`, polled every 10 s).

This change combines them: a durable leased queue like media jobs, whose work runs as the
initiator like the log import.

Two existing rules this change must respect explicitly:
- ADR 0031 (show-wiki-ai) lists "a background run is wanted (that would need a non-human author
  and a different credential story)" as a revisit trigger. Auto-accept is that background run.
  D12 and ADR 0033 answer it: the author is the human initiator who confirmed the batch, the
  credential is the initiator's own, and the revision is marked as batch.
- core-ports-architecture "Every catalog and session call is bound to a caller": the catalog user
  binding may be created only by the auth middleware (enforced by
  `server/src/catalogSystem.repo.test.ts`). The worker is a second, reviewed creator (delta in
  `specs/core-ports-architecture`).

## Goals / Non-Goals

**Goals:** a manager starts one job for many sessions; the job fills only gaps, in episode order,
on the initiator's credentials, as the initiator, surviving restarts and multiple processes; a
manual run on the same session is never corrupted; every refusal of the manual routes still
applies; the report never leaks provider output.

**Non-Goals:** speed (one session at a time per job by decision); a spend ledger; regeneration;
push notifications; changing any manual route's observable behaviour.

## Decisions

### D1. Two tables, written in one migration

`supabase/migrations/20261025000000_autogenerate_jobs.sql`:

```sql
create table catalog.autogenerate_jobs (
  id                     text collate "C" primary key,
  team_id                text collate "C" not null references catalog.studio_definitions (id),
  initiator_user_id      text collate "C" not null references catalog.users (id),
  initiator_name         text collate "C" not null,
  scope                  text collate "C" not null check (scope in ('shows', 'sessions')),
  show_ids_json          text collate "C",                       -- null for 'sessions'
  steps                  text collate "C" not null,              -- e.g. 'transcript,events,topics,wiki'
  wiki_mode              text collate "C" not null check (wiki_mode in ('accept', 'pending')),
  status                 text collate "C" not null default 'queued'
                           check (status in ('queued', 'running', 'finished', 'cancelled', 'failed')),
  stop_reason            text collate "C" check (stop_reason in ('cancelled', 'initiator-unavailable',
                           'initiator-role-lost', 'not-approved', 'unconfigured-stt', 'unconfigured-llm')),
  session_count          integer not null check (session_count between 1 and 1000),
  locked_by              text collate "C",
  locked_until_ms        bigint,
  cancel_requested_at_ms bigint,
  cancel_requested_by_user_id text collate "C",
  cancel_requested_by_name    text collate "C",
  created_at_ms          bigint not null,
  started_at_ms          bigint,
  finished_at_ms         bigint,
  updated_at_ms          bigint not null,
  constraint autogenerate_jobs_stop_reason check ((status in ('cancelled', 'failed')) = (stop_reason is not null))
);
create unique index idx_autogenerate_jobs_live on catalog.autogenerate_jobs (team_id)
  where status in ('queued', 'running');
create index idx_autogenerate_jobs_team on catalog.autogenerate_jobs (team_id, created_at_ms desc);
create index idx_autogenerate_jobs_due on catalog.autogenerate_jobs (created_at_ms)
  where status in ('queued', 'running');

create table catalog.autogenerate_items (
  job_id          text collate "C" not null references catalog.autogenerate_jobs (id) on delete cascade,
  session_id      text collate "C" not null,                     -- no FK: the report outlives a session
  step            text collate "C" not null check (step in ('transcript', 'events', 'topics', 'wiki')),
  ordinal         integer not null,                              -- the session's processing position
  step_order      smallint not null,                             -- 0..3, transcript..wiki
  effective_date  text collate "C",
  status          text collate "C" not null default 'pending'
                    check (status in ('pending', 'running', 'done', 'skipped', 'failed', 'cancelled')),
  outcome         text collate "C",                              -- one of the contract's fixed codes
  attempts        smallint not null default 0,
  run_ids         text collate "C" not null default '',          -- events/wiki run ids this item used
  wiki_accepted   integer,
  wiki_pending    integer,
  started_at_ms   bigint,
  finished_at_ms  bigint,
  primary key (job_id, session_id, step),
  constraint autogenerate_items_outcome check (outcome is null or outcome in (<the 19 codes>))
);
create index idx_autogenerate_items_order on catalog.autogenerate_items (job_id, ordinal, step_order);
```

- **Fixed vocabularies in the database.** Outcomes and stop reasons are check-constrained to the
  contract's codes; details are looked up from the code in `packages/contract`, never stored. So
  no column can hold provider text (owner decision 5), the way `media_jobs_error_code` does.
- **No credential column.** The initiator is only `initiator_user_id` (owner decision 6). The
  name is a snapshot, as wiki rows do.
- **`run_ids`** is a comma list (at most 3 interrupted attempts + 1) so a resumed item can find its
  own partial output (D7).
- **The live index** gives "one running job per studio" as a database fact: two concurrent starts
  collide on `23505`, which the route maps to the first `409`.
- Times are Clock epoch milliseconds, like media jobs; the routes format them as ISO strings.
- Rollback in the header (a documented step, as the other migrations): `drop table
  catalog.autogenerate_items; drop table catalog.autogenerate_jobs;` after the code is reverted.

*Alternatives.* A kv record per job (the log-import pattern): rejected, kv records expire and
cannot express the per-team uniqueness or a per-item report. One item per session with four
status columns: rejected, the per-step outcome and attempts would need four columns each.

### D2. Row-level security: managers read, initiators insert, managers may only request a cancel

- RLS on both tables; the usual `<table>_system_all` policy for `catalog_system`.
- `catalog_user` **select**: `team_id in (select catalog.manager_studios(catalog.app_user_id()))`
  (items through their job). A demoted admin stops seeing the team's jobs at once.
- `catalog_user` **insert** on jobs: `initiator_user_id = app_user_id()`, `status = 'queued'`,
  team managed by the caller, no lease or cancel or stop columns set. Items: the job is the
  caller's own `queued` job. The start route therefore writes the job and its items **as the
  caller**, in one user-bound transaction, and the database itself proves the caller manages the
  team at commit time (the route also checks the role first for the frozen `403`).
- `catalog_user` **update** on jobs: column grant on `cancel_requested_at_ms`,
  `cancel_requested_by_user_id`, `cancel_requested_by_name`, `status`, `stop_reason`,
  `finished_at_ms`, `updated_at_ms`; policy: team managed by the caller. A `before update`
  trigger `autogenerate_jobs_user_guard`, for `current_user = 'catalog_user'` only, allows exactly
  (a) setting the cancel columns once, to the caller, on a `queued` or `running` job, and (b) for
  a `queued` job in the same statement, `status → 'cancelled'`, `stop_reason → 'cancelled'`,
  `finished_at_ms` set. Anything else raises `42501`. No user update on items; no user delete.
- The worker uses `system('autogenerate-worker')` for claims, lease renewals, item and job
  transitions, and the initiator re-read (D4). That reason joins the reviewed allowlist.

### D3. The worker: a leased loop in every API process

`server/src/autogenerate/worker.ts`, started from `main.ts` beside `startMediaApply`, stopped in
the shutdown sequence:

- **Claim** (one job per process at a time): `update autogenerate_jobs set status = 'running',
  locked_by = $me, locked_until_ms = $now + 60000, started_at_ms = coalesce(started_at_ms, $now)
  where id = (select id from autogenerate_jobs where status = 'queued' or (status = 'running' and
  locked_until_ms < $now) order by created_at_ms for update skip locked limit 1) returning *`.
  A claimed `queued` job with a cancel already requested ends `cancelled` at once.
- **Lease.** Renewed every 10 s, fenced on `locked_by = $me and status = 'running'`. A renewal
  that changes no row means another process took the job over: this process stops after its
  current step and writes nothing more (each item and job write is fenced the same way).
- **Wake-up.** The start route sends `pg_notify('autogenerate_jobs', '')` after commit; the worker
  also polls every 15 s, so a restarted process picks up a lapsed job within 60 s + 15 s.
- **Order.** Items are read in `(ordinal, step_order)` order; the first item not ended is next.
- One session at a time inside a job (owner decision 4); across processes, two teams' jobs may run
  at once (Open question Q6).

*Alternative.* A separate worker container like the media worker: rejected, the work needs the
API's providers, session hub, slot registry and provider-key cipher; a second process type would
need all of them and the provider-key secret.

### D4. Acting as the initiator, with no stored secret

The job row is the whole authority record: `initiator_user_id`. Before each session the worker:

1. reads the account with `authGetUserById` under `autogenerate-worker` (`null` for a missing or
   disabled account → stop `initiator-unavailable`);
2. builds `AuthUser` from that row and derives `sys.forUser(userId)` and `userCaller(userId)`,
   exactly what the auth middleware builds for a request;
3. resolves provider credentials per step from the user (`resolveSttCredential(env, userId)`,
   `resolveLlmRoute(env, user)`), so a key change, a removal, or a change to `CLAUDE_CLI_EMAILS`
   applies from the next step, as for a request.

No token is minted and nothing is copied into the job: the server already holds every user's
encrypted keys (ADR 0027) and decrypts them per use; the worker uses the same path. The trust
assumption is the one the log-import job already makes: server-side code may act for a user who
started work and is still entitled to it, which D5 re-checks.

### D5. The per-session gate ladder

Mirrors the manual routes' order, with job-level refusals where every later session would fail the
same way:

| # | Check (as) | Refusal |
| --- | --- | --- |
| 0 | cancel requested (system) | job `cancelled`; remaining items `cancelled` / `cancelled` |
| 1 | account enabled (system re-read, D4) | job `failed` `initiator-unavailable`; remaining items `cancelled` / `job-stopped` |
| 2 | initiator is owner/admin of the team (user binding, `authGetMembershipRole`) | job `failed` `initiator-role-lost` |
| 3 | approved user (`runFeatureAllowed`) | job `failed` `not-approved` |
| 4 | session exists, not deleted, show in the team, `authCanAccessShow` (user binding) | session's items `skipped` `session-gone` / `access-lost`; continue |
| 5 | per step: gap (D7) | item `skipped` `present` |
| 6 | per step: credential (D4) | item `failed` `unconfigured`; job `failed` `unconfigured-stt` / `-llm` |
| 7 | per step: preconditions, the route's own (no audio, no words, no anchors, no instructions, instruction bound) | item `skipped` with the code; dependent steps `skipped` the same |
| 8 | per step: single-flight (D8) | wait, then `busy` |
| 9 | per step: gap again under the single-flight | item `skipped` `present` |
| 10 | run (D6) | `done`, or `failed` with a code (D9) |

Step 4 runs before every session even when steps 1-3 pass, as the security floor (owner decision
6); it is the same predicate the session routes' masked 404 uses (`requireSession`). Steps 2-3 are
stricter than the owner asked (Q1).

### D6. One implementation per step: runners shared by the route and the worker

Each generate route is split into a context-free runner in `server/src/generation/` and a thin
route adapter:

```ts
interface GenerationPrincipal { user: AuthUser; catalog: CatalogFacade; caller: SessionCaller;
                                env: Bindings }
runTranscript(p, sessionId, opts: { onlyIfEmpty?: boolean; signal? }) → TranscriptOutcome
runEvents(p, sessionId, opts: { selection?, regenerate?, ownRunIds?: string[], runId? }) → EventsOutcome
runTopics(p, sessionId, opts) → TopicsOutcome
runWiki(p, sessionId, opts: { runId? }) → WikiOutcome
```

Each outcome is a discriminated union of the route's refusals and results (`unconfigured`,
`forbidden`, `precondition:<code>`, `busy`, `failed:<code>`, `ok`). The route maps them to its
frozen statuses and details, unchanged; `sdkTurnSpec`/`callerLlmRoute` take `(env, user)` instead of
`c`. Existing route tests (`transcribe.int.test.ts`, `events.generate.int.test.ts`,
`wikiSuggestions.int.test.ts`, the topic tests) are the regression net and must pass unedited.

*Why not call the routes over HTTP from the worker?* It would need a session cookie for the
initiator (a stored credential, refused by decision 6) and could not express the gap guards.

### D7. "Missing", per step, and the job's own partial output

- **transcript**: `listTranscriptWords().length === 0`. The runner gains `onlyIfEmpty`: inside the
  existing replace transaction (`replaceTranscriptWordsRemapped`) it re-counts the words and, if
  any exist, throws a sentinel that rolls back and maps to `present`. The paid call is then wasted
  but no word is overwritten (owner decision 2).
- **events**: missing when no event is auto-generated, ignoring events whose
  `auto_generate_run_id` is in the item's `run_ids` (its own interrupted or failed attempts). A
  run records its fresh run id in `run_ids` **before** the turn. On success it deletes the events
  of the item's earlier run ids (delete-after-success, like `regenerate`, but limited to its own
  ids). On failure it deletes the events of its own run id, through the same `session-undo` path the
  route uses for its regenerate snapshot, so a failed step leaves the session "missing" for a later
  job. The run is never `regenerate` and never passes a selection: every instruction-bearing
  category runs.
- **topics**: missing when `listTopics().length === 0`. The runner's crash-safe swap already
  deletes the pre-run topics on success; on a first attempt the pre-run set is empty; on a resumed
  attempt it is the interrupted run's partial topics (and see Risk R6).
- **wiki**: always runs when the session has words. The item records its run id before the turn. On
  resume, if any suggestion with that run id exists, generation is done; only the accept phase
  (D12) continues. Otherwise a fresh run id is used.

### D8. Busy: wait, then skip the session

The runner's single-flight refusal (`busy`) and a live `recording` lease (`leaseStatus().lease_alive`)
both mean busy. The worker retries the step every 15 s, re-checking the cancel and the job lease,
for up to 10 minutes from the first refusal, then marks the item and the session's remaining items
`skipped` `busy` and moves on. Nothing is queued for later (Q4). Within one process the worker's
step and a human's request contend for the same in-process slot; across processes, for the same
run lease, so a batch step and a manual run never overlap on a session.

### D9. Failure classification

| Runner outcome | Item | Session's later steps |
| --- | --- | --- |
| transcript `no_audio` | `skipped` `no-audio` | dependants `skipped` `no-transcript` |
| transcript `no_speech` | `skipped` `no-speech` | dependants `skipped` `no-transcript` |
| transcript `upstream` | `failed` `provider-failed` | `skipped` `earlier-step-failed` |
| transcript `oversize` | `failed` `too-large` | same |
| transcript `missing_blob` | `failed` `missing-audio-file` | same |
| transcript `unreadable` | `failed` `unreadable` | same |
| events/topics/wiki turn failure, timeout, incomplete page coverage, store failure | `failed` `generation-failed` | same |
| any unexpected throw | `failed` `generation-failed`, logged with the session id and error class only | same |
| interrupted 3 times | `failed` `interrupted` | same |

Logs follow the routes' content-free pattern (`[autogenerate] job=<id> session=<id> step=<s>:
<code>`), never provider text, prompts or paths.

### D10. Cancel

The cancel route writes the cancel columns as the caller (D2). The worker checks the cancel
before each session and each step and between busy retries; it never aborts a provider call (the
manual routes pass no abort signal either). When the step in progress ends, its result is kept and
recorded, then the job ends `cancelled` and every non-ended item becomes `cancelled`/`cancelled`.

### D11. Resume

A process that dies leaves its job `running` with a lapsing lease and possibly one item
`running`. The next claim continues from the first non-ended item. A `running` item is re-entered
with `attempts + 1`; at the fourth entry it is `failed` `interrupted`. Re-entry runs the full
ladder (D5) again, including the gap check with D7's own-output rules, so it is gap-fill by
construction. The session's run leases of the dead process lapse after 40 s (A11), before the
job's 60 s lease, so the resumed step does not see its own ghost as busy.

### D12. Wiki auto-accept

`WikiSuggestionStore.acceptSuggestion` gains an optional `{ batchJobId }`, used only by the worker:
it appends ` (batch <job id>)` to the note, and nothing else changes (same transaction, same
compare-and-set, same link checks, same `resolved_by`). For each suggestion of the item's run id
that is still `pending`, in proposal order, the worker calls it as the initiator with
`expectedRevision = base_revision` (a new page needs none). Any wiki error (stale, merged, deleted,
clash, session page exists, invalid link) leaves the suggestion pending and counts it in
`wiki_pending`. Each accept is its own transaction, so one refusal does not undo another accept.

This is the trust boundary of the change. A person's accept is a reviewed act on a diff; a batch
accept is a pre-authorisation, given once in the confirm, for text the person will not read first.
What still holds: every new quote was checked against the transcript at proposal time (ADR 0031),
the page rules and link checks run, the author is the human who confirmed, the note marks it, and
the history allows a revert. What does not: a true quote supporting a false or injected claim
(transcripts are untrusted input) reaches the live page, visible to every member of the show,
without review. See R1.

### D13. Ordering

`effective_date` is computed in SQL at start (`episode_date` if it matches `^\d{4}-\d{2}-\d{2}$`,
else `left(started_at_utc, 10)`, else `left(created_at_utc, 10)`, each only when it matches) and
stored per item with the ordinal from `order by effective_date nulls last, started_at_utc,
created_at_utc, id` (all `collate "C"`).

### D14. Routes

`server/src/routers/autogenerate.ts`, mounted with the team routes, reusing `requireTeamRole(c,
teamId, OWNER_OR_ADMIN)` (exported from `teams.ts` or moved to `_helpers.ts`) so the `401` /
masked `404` / `403` prefix is byte-identical to the team family. Contract schemas in
`packages/contract/src/autogenerate.ts`. The candidate query is one SQL statement under the
caller's binding, so RLS bounds it; the session-list scope checks each id with the same query and
masks a miss as `404 Session not found`. `startAutogenerateJob(principal, scope)` (the service the
route calls) is the hand-off point for the playlist import (proposal "Follow-up"); it re-runs every
start check itself.

Preview counts "missing" with three grouped `exists` queries over the session content tables for
the candidate ids, under the caller's binding.

### D15. Settings section

`BatchAutogenerateSection.tsx` in the Team group (`sections.ts`, `SettingsSections.tsx`); the nav
filters it out unless `profile.teams` has a role `owner`/`admin` (the profile's teams carry `role`,
api-contract-freeze "Profile teams role field"). Hooks in `web/src/api/hooks/useAutogenerateJobs.ts`
(TanStack Query): preview debounced 400 ms on scope changes; job detail polled every 5 s while a job
is live and the section is visible; the confirm and the cancel use the themed confirm
(web-ui-system "Themed confirmations replace browser chrome"). The section acts immediately (no save
bar), like Companion devices.

### D16. ADR 0033

`docs/decisions/0033-batch-autogenerate-jobs.md`: a durable leased job that acts as its human
initiator with no stored credential, the per-session re-check, the wiki pre-authorised accept (and
how it answers ADR 0031's revisit trigger), and what would reverse it.

## Risks / Trade-offs

- **R1 [Trust boundary: auto-accept] Unreviewed AI text, possibly steered by an injected
  transcript, lands in live wiki pages.** → The owner chose `accept` as the default (decision 8).
  Mitigations: the confirm names it explicitly; quotes are verified; stale or clashing suggestions
  stay pending; every batch revision is marked `(batch <job id>)` and attributable; the history
  reverts it. Residual recorded in `docs/security.md`. The panel should weigh whether the default
  should be `pending`; this design does not change the owner's decision.
- **R2 [Spend] A job can make up to 4000 paid runs on the initiator's accounts, possibly for days.**
  → 1000-session cap, the estimate and confirm, per-turn bounds of each step, cancel by any
  manager. No job-level budget (Q5). A manager may start a job that spends another manager's
  money? No: a job always spends its **initiator's** credentials; another manager can only cancel.
- **R3 [Wiki re-runs] A second job over an already-filled show re-runs the wiki update on every
  session** (wiki is never "present", decision 2), costing money and superseding pending
  suggestions. → The estimate shows wiki runs = all sessions. Q9.
- **R4 [Batch supersedes human-pending suggestions]** A batch wiki run supersedes a pending
  suggestion a person's earlier run stored for the same page and, in `accept` mode, accepts the
  carried-forward text. → Same rule as a manual run (show-wiki "One pending suggestion per
  target"); the note marks the accept.
- **R5 [Manual users see a plain 409]** While a batch step holds a session, the manual routes
  answer their existing busy text, which does not name the batch (kept frozen, as ADR 0031 did). →
  The transcript status endpoint and the Settings section show the running job.
- **R6 [Topics resume]** A human topic added to a session during the crash window of an
  interrupted topics step is deleted by the resumed run's success swap. → Narrow window (a crash
  during a topics turn on a session that had no topics); recorded.
- **R7 [Wasted paid call]** A transcript discarded by `onlyIfEmpty`, or a step that lost its job
  lease, still cost a provider call. → Rare; correctness over cost.
- **R8 [Long cancel latency]** Cancel waits for the current step (up to the wiki timeout, 900 s). →
  Owner decision 7; the section says "stopping after the current step".
- **R9 [Credentials of a departed manager]** A job keeps spending its initiator's credentials
  after the initiator stops paying attention. → The initiator sees it in the section; D5 steps 1-3
  stop it when the account is disabled, demoted or unapproved.
- **R10 [Two processes, one job]** A process that lost its lease (long GC, network) may finish a
  step while another resumes the job. → Item and job writes are fenced on `locked_by`; the
  session's run lease prevents two runs on one session; the resumed step's gap check sees the
  output and records `present`.
- **R11 [Importer pin]** The new migration moves the legacy importer's `TARGET_SCHEMA_VERSION`
  (as in closed-signups task 1.2). → Task 1.4.

## Migration Plan

1. Deploy: the migration creates two empty tables; the worker finds nothing to claim.
2. No KV or secret change.
3. Rollback: cancel live jobs (or wait), revert the code, then drop the two tables (the migration
   header). Pages accepted by jobs keep their revisions.

## Open Questions

Recorded for the owner and the panel; each has the default this design implements.

- **Q1. Role loss mid-job.** Default: demotion below admin, leaving the team, losing approval or a
  disabled account stops the whole job (D5 steps 1-3), stricter than "skip the session". Owner may
  prefer continuing under the per-session access check only.
- **Q2. Credential loss mid-job.** Default: stops the job (`unconfigured-*`) rather than failing
  every remaining session one by one.
- **Q3. Undated sessions.** Default: fall back to the start date, then the creation date; truly
  undated sessions last. Alternative: undated always last.
- **Q4. Busy numbers.** Default: retry every 15 s for 10 min, then skip the session with no
  second pass. Alternative: requeue busy sessions once at the end of the job.
- **Q5. Spend cap.** Default: none beyond the 1000-session cap and per-turn bounds. A per-job
  budget would need the AI SDK's usage reports summed per job.
- **Q6. Parallel jobs across teams.** Default: one job per process, so with one API process teams
  queue behind each other. Alternative: a small per-process pool, still one job per team.
- **Q7. Retention.** Default: keep every job and item; the list returns the newest 20. A sweep can
  come later.
- **Q8. Archived sessions.** Default: included (only deleted sessions are excluded).
- **Q9. Wiki on already-filled sessions.** Default per decision 2: always runs. Option: an "only
  sessions with no wiki suggestion from any run yet" toggle, if R3 proves costly.
- **Q10. Auto-accept default.** Owner decision 8 makes `accept` the default; the panel is asked to
  confirm the residual (R1) is accepted, not to change it.
