# Panel: show-wiki-ai
Tier: 2 · Reviewers: assumption tester, failure and abuse, scope and simplicity · Date: 2026-10-13

- [x] [critical] Reference-style citations bypass the quote check: `parseWikiLinks` reports only the `definition` label, so `[fabricated quote][the]` + `[the]: cite:S1@120` passes, and reusing a base definition skips the check entirely (assumption tester and failure and abuse). Evidence: `parseWikiLinks('He said [we never said that][the] …\n\n[the]: cite:S1@120')` -> `[{"source":"definition","label":"the"}]`. Resolved: new contract `citationsOf` returns every rendered citation (links and full/collapsed/shortcut `linkReference`s to a `cite:` definition) with its rendered text; the check and the "kept" key use that text (wiki-generation "Proposals are checked when they are made", scenario "A reference-style citation is checked by its text"; design D4 step 4; task 4.2).
- [x] [critical] A full rewrite of up to 100,000 characters can't fit in one step's 16,000 output tokens, so a long page caps the step and the run stores nothing (scope and simplicity). Evidence: `server/src/env.ts:142` -> `intInRange(env.GENERATE_MAX_OUTPUT_TOKENS, 1000, 128_000, 16_000)`. Resolved: AI proposals are capped at 30,000 characters (about 8–10k tokens); pages over 30,000 can't be AI-rewritten and reads are cut and marked at 30,000 (spec "The wiki turn and its tools", "Proposals are checked…"; design D3/D4; non-goal).
- [x] [critical] Topic generation's 40-step cap plus store-only-on-success throws away ordinary wiki runs (scope and simplicity). Evidence: `server/src/env.ts:140` -> `intInRange(env.GENERATE_MAX_STEPS, 1, 100, 40)`. Resolved: own `WIKI_GENERATE_MAX_STEPS` (default 80, 1–200) and `WIKI_GENERATE_MAX_TOKENS` (default 6,000,000); the target cap goes from 30 to 20; scenario "A realistic run fits the bounds" and task 4.4 test it.
- [x] [critical] New-page proposals keyed by `search_norm(title)` in ai-runtime can't be built: `search_norm` is SQL-only, and a TS approximation could disagree with the pending unique index and make `saveRun` fail (scope and simplicity). Evidence: design D3/D4 (first draft); catalog-database delta pending index on `search_norm(title)`. Resolved: `WikiToolPort.normalize` calls `catalog.search_norm` in one SQL query; keys, name checks and the quote match all use it (design D2/D3).
- [x] [major] The quote check filters on `start_sec`, which the model never sees, and which manual inserts and remaps leave at 0 (assumption tester). Evidence: `transcriptStore.ts:142` inserts without `start_sec`; `transcriptRemap.ts:240` -> `start_sec: 0`; snapshot word has `word; session_time; speaker`. Resolved: the match runs over the run's word snapshot, using each word's `session_time` timecode as `HH×3600+MM×60+SS` (frames dropped), with `start_sec` only as the fallback; the prompt states the conversion (design D4 step 5; A4–A6).
- [x] [major] A newer run supersedes an older pending suggestion the model never saw, silently dropping unreviewed work (failure and abuse). Evidence: first-draft D3 tool set had no suggestion reader. Resolved: `read_wiki_page` returns the page's pending suggestion and reads pending new-page suggestions by id; `list_wiki_pages` flags them; the prompt says to build on them (scenario "A pending suggestion is carried forward"; show-wiki "AI suggestions").
- [x] [major] Tool results and pages overflow bounds: `read_wiki_page` up to 100k characters and `list_wiki_pages` rows of 50×200-character aliases exceed the CLI's ~50k tool-output limit, so the model could rewrite a page it never saw (failure and abuse). Evidence: `aiMcpServer.ts:440-450` `GENERATION_PAGE_MAX_CHARS = 45_000`; `schemas.ts:667` `WIKI_BODY_MAX = 100_000`. Resolved: lists pack to 200 lines and 40,000 characters, reads cut at 30,000 and mark it, and a page over 30,000 can't be a target (spec; design D3; task 4.3 adversarial fixture).
- [x] [major] `search_show` shares the process-wide 2-slot search pool with human search and can starve it, and `checkQuotes` ran up to 200 unindexed window queries per proposal (failure and abuse); `search_show` and other-session quotes also exceed "from this session" and mismatch the lockdown text (scope and simplicity). Evidence: `searchStore.ts:126` `new SearchSlots(2, 1000)`; `explain analyze` -> `Seq Scan … Rows Removed by Filter: 31742`. Resolved: `search_show` is cut; new citations must quote the run's own session and are matched in memory over the snapshot, with one normalise query per run (spec; design D4; non-goals; ai-topics-chat delta now seven tools).
- [x] [major] One `accessible_shows` policy for select/insert/update lets a member forge `created_by`/`resolved_by`, reopen resolved rows, or rewrite a body after its quotes were checked (failure and abuse). Evidence: `20261021000000_show_wiki.sql:105-112` pins `author_user_id` and revokes update on revisions; first-draft D1 did neither. Resolved: separate select/insert/update policies; insert pins `created_by = app_user_id()` and `pending`; update only from `pending`, to `superseded` or to accepted/dismissed with `resolved_by = app_user_id()`; update granted only on the status and resolved columns; scenarios added to the catalog-database delta and task 2.1.
- [x] [major] The "no show" `400` is unreachable: `requireSession` already returns the masked 404 for a session with no show (assumption tester). Evidence: `_helpers.ts:86-104` -> `if (!showId || !(await catalog.auth.authCanAccessShow(…))) throw new ApiError(404, 'Session not found')`. Resolved: the 400 row and scenario are removed; the 404 row says "has no show".
- [x] [major] The pinned policy count would go 42 → 43 per new `catalog_user` policy, not by the system policy (assumption tester). Evidence: `catalogPolicies.pg.test.ts:596-604` counts `'catalog_user' = any(roles)`; DB -> `42|72`. Resolved: with three `catalog_user` policies the count is 42 → 45 (design D1, D7, task 2.2).
- [x] [major] `propose_page` checked linked pages by `readPage`, which refuses deleted pages, so it was stricter than a manual save (assumption tester). Evidence: `wikiStore.ts:18-21` "deleted or merged pages are allowed". Resolved: links go through the store's own `checkLinks` via the port (design D2/D4; task 3.2).
- [x] [major] The new env vars can't reach the stack: the tasks missed the `Config` type, the loader, the compose allowlist, `.env.example` and the full-`Config` test fixture (assumption tester). Evidence: `grep TOPIC_GENERATE_TIMEOUT_SEC` -> `ports/src/config.ts:59`, `node/config.ts:231`, `upgradeDispatch.test.ts:44`; `compose-run.mjs:36` `ALLOWLIST = 'docker/secrets-env.yaml'`. Resolved: task 5.1 wires all four vars through those files and checks them in the dev container; D7 category 6 covers the fixtures.
- [x] [major] Accept had no `kind` override, while the spec said "(or the edited) kind", and nothing said how a new-page suggestion is edited (scope and simplicity). Resolved: the kind can't change on accept (contract delta); the editor opens in a draft mode with the kind fixed (show-wiki "Suggestions inbox"; design D6; task 6.4).
- [x] [major] The proposal shape check listed only some page limits, so a stored suggestion could be unacceptable (scope and simplicity). Evidence: show-wiki `spec.md:24-28`. Resolved: "every page limit of a manual save", plus no aliases on a session page; task 4.1 covers each.
- [x] [major] The wiki turn's paged rendering was extended by reference only, while auto-event-generation limits generation density to event and topic runs (scope and simplicity). Evidence: `auto-event-generation/spec.md:374`. Resolved: a MODIFIED auto-event-generation delta names the wiki turn, and wiki-generation states the snapshot, stability and coverage rules itself.
- [x] [major] Diffing "against the base revision unless stale" is redundant: not-stale means current equals base (scope and simplicity). Resolved: the sheet always diffs against the current revision and says when the page changed since (show-wiki delta; design D6; task 6.4).
- [x] [major] Clauses without tests: the wiki hard cap, waiting for running tool bodies, a failed `saveRun`, and the CLI side of "Chat turns cannot use the wiki tools" (scope and simplicity). Resolved: tasks 4.4 and 5.1 name each test, and scenario "A failed store stores nothing" was added.
- [x] [major] "Next to 'Wiki page'" could break show-wiki "Wiki screens", which puts "Wiki page" at the end of the feed-tab row (scope and simplicity). Evidence: `openspec/specs/show-wiki/spec.md:219`. Resolved: "Update wiki" goes immediately before "Wiki page", which stays last (show-wiki delta; design D6; task 6.3).

## Re-panel 2026-10-14
Delta: carrying a pending suggestion's citations forward, and one body per `read_wiki_page` result (found while implementing task 4.3). Reviewers: failure and abuse; assumption tester + scope (combined); then a fresh failure and abuse + consistency reviewer on the revised delta.

- [x] [major] Task 4.3 as specified refused a carried-forward suggestion's citations of the earlier session, defeating "A pending suggestion is carried forward"; and a page read returning page + suggestion bodies could reach about 60,000 characters, over the CLI's 45,000 bound (implementation subagent). Evidence: `packages/ai-runtime/src/wikiTools.ts:548-565` (`kept` from the base body only). Resolved: carried-forward citations may cite a session the target's pending suggestion cites and are re-checked against that session (wiki-generation "Proposals are checked when they are made"); `read_wiki_page` returns one body per call, with the pending suggestion's id on the page read.
- [x] [major] The first draft's fix exempted pending-suggestion citations as "already checked", but a pending body can hold citations its run kept unchecked from an older base (since removed from the page), and the exemption chains run to run (failure and abuse). Evidence: `wikiTools.ts:548-565`. Resolved: no exemption; anything not in the current base body is checked (design D4 step 4, scenario "A carried-forward misquote is refused").
- [x] [major] Nothing in the database proves a pending row went through `propose_page`'s checks, so trusting pending bodies relied on `saveRun` being the only insert path (failure and abuse). Evidence: migration lines 72-92 (insert policy allows any body); `wikiSuggestionStore.ts:268-321` (no quote check). Resolved: same fix; pending bodies are never trusted for the quote check.
- [x] [major] One result's header isn't bounded: JSON-escaped aliases double, so a 30,000-character body plus 50 escaped 200-character aliases reaches about 50,692 characters (assumption tester). Evidence: `node -e …` -> `escaped worst 50692 plain worst 40371`. Resolved: the body is cut further so the whole rendered result is at most 45,000 characters; task 4.3 adds the adversarial-header fixture.
- [x] [major] For a new-page target nothing fetched the pending body, so carry-forward couldn't work for new pages (assumption tester). Evidence: design D4 step 2 had no pending read; the port lacked `pendingFor`. Resolved: `port.pendingFor({pageId}|{normTitle})` for both target kinds; task 4.3 tests both.
- [x] [major] The security filters the delta adds (`sessionWords` only for the run's show, `readPending` only pending rows of the run's show) were tested only over a fake port, while RLS alone allows other accessible shows (fresh reviewer). Evidence: tasks 3.2/4.3/5.1 text; `session_transcript_words_user_all` uses `accessible_shows`. Resolved: task 5.1 tests the real `_wikiToolPort` with a member granted on two shows, including a directly inserted pending row citing the other show.
- [x] [major] The design's rejected alternative still said other-session quoting was cut as an oracle, and "can't probe arbitrary sessions" overstated the limit, since a member can insert a pending row citing any session of the show (fresh reviewer). Evidence: design.md D4 alternatives vs step 4. Resolved: both rewritten to state the trade-off: a pass/fail oracle within the caller's own access.
- [x] [major] The ai-topics-chat "Session-scoped MCP toolset" header still said the model can't address another session, contradicting the amended lockdown bullet (fresh reviewer). Evidence: `specs/ai-topics-chat/spec.md:6-9` vs `:167-171`. Resolved: the header names the one other-session read and that it answers only pass or fail.
