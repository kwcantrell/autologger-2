# event-metadata-reserved-keys — design

## Context

`logBodySchema.metadata` is `z.record(z.unknown())` with only a serialized-size
cap; the POST handler merges server-side UI snapshots into it and stores the
result. The auto predicate (`isAutoGeneratedMetadataJson` / the store's SQL
predicate, parity-pinned) treats `auto_generated === true` as
generation-attributed; `event-generate-hardening` built `has_auto_generated`,
the Regenerate label, and the regenerate snapshot sweep on it. No in-repo
client sends non-empty metadata on this POST (sole sender:
`useRecoveryStopWarning`, `{}`); the sheets importer writes via the hub, not
the route; PUT carries no metadata field.

## Goals / Non-Goals

**Goal:** the auto predicate reflects only server-attributed rows for new
writes. **Non-Goals:** see proposal (no allowlist, no retro cleanup, no
PUT/WS work, no cap change).

## Decisions

### D1 — Silent strip, not 400

Alternatives: (a) 400 on reserved keys; (b) strip. Chosen: strip — matches the
repo's ignore/strip precedent (session-title-suffix D8), keeps stale/external
clients working (the frozen-surface non-loophole), and the keys have no
legitimate client meaning. A 400 would add a detail string and a new failure
mode for zero benefit.

### D2 — Strip site and shared constant

The strip happens in the POST handler after zod parse and before the UI-snapshot
merge, deleting exactly the two reserved keys from the parsed metadata object.
The key list lives in ONE exported constant beside the JS predicate in
`events.ts` (`AUTO_GENERATION_RESERVED_METADATA_KEYS`), imported by the strip
and referenced by tests — one place to extend if generation ever grows keys.
The size-cap refine runs on the body as sent (pre-strip) — stripping never
*creates* an over-cap failure, and keeping the cap's input stable avoids an
observable cap-behavior change.

### D3 — No retroactive cleanup

Pre-existing client-stamped rows keep matching the predicate; the next
regenerate sweeps them (recorded in the delta). A migration rewriting metadata
would be a destructive data op for a corner already self-healing.

## Risks / Trade-offs

- External clients that intentionally stamped the keys lose that (undocumented)
  ability — that is the point; recorded as the single observable change.
- The strip is object-shape–dependent: metadata arrives as a zod record, so
  only top-level keys are reserved (nested `{ x: { auto_generated: true } }`
  never matched the predicate anyway — predicate reads `$.auto_generated`).
- Key-literal drift (accepted residual): the reserved keys are also spelled
  literally in `aiMcpServer.ts`'s `create_event` merge and both predicates —
  a future generation key means multiple edit sites; the tasks' constant⊇
  predicate-key tripwire test bounds the worst drift.
