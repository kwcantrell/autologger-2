# Panel: fix-companion-device-cap
Tier: 2 · Reviewers: queue design and scope, concurrency and adapter, scope tests and repo rules · Date: 2026-10-12

- [x] [major] The per-user queue wait was unbounded and outside the adapter's `txTimeoutMs`: the Nth create could wait about (N-1)×10 s, and a disconnected client's create still inserted later with a token it never received. Evidence: `companionDevices.ts` create, `postgresCatalogStore.ts` deadline inside `tx()`. Resolved: a create that cannot start its transaction within the adapter's `txTimeoutMs` fails with the adapter's `CatalogTxTimeoutError` and never inserts (same generic 500 as a transaction timeout); total bounded at about 2× the timeout; no abort signal (the store port has none), documented in Non-goals; tasks 2.2, 2.3.
- [x] [major] A synchronous throw in the queued turn (clock throws, NaN `toISOString`) left the create unsettled, made every later create for that user time out, leaked the map entry and could raise an unhandled rejection. Evidence: create turn callback, `insertCapped`. Resolved: the turn runs inside `Promise.resolve().then(...)` and the chain and cleanup use `.then(cb, cb)`; a throwing clock rejects that create only, the next create succeeds and the map ends empty (red: never settled, unhandled `Error: clock failed`); task 2.7.
- [x] [major] Process order: Tier 2 needs `panel.md`, the owner's `Approved-by:` and an artifacts-only first commit. Resolved: `de196335` holds only the change directory with unticked tasks; this panel; approval is the owner's step.
- [x] [minor] `createdAt` was read before the queue wait. Resolved: read when the create's turn comes; task 2.4.
- [x] [minor] Single-process assumption: `config.ts:193` builds one store per process and the API is one process per env (DataDirLock); a second API process falls back to serializable retries (cap still holds). Resolved: stated in Non-goals.
- [x] [minor] Test robustness: the waiter test's transaction has the 10 s deadline and sits through a 2 s second wait, so a slow first-waiter detection on loaded CI can time it out. Evidence: `companionDevices.pg.test.ts` ~246. Resolved: that test's adapter has a 120 s transaction timeout, so the lock holder outlasts both waits; task 2.8.
- [x] [minor] No route-level test pins the original 500 (the route test with default retries only reproduces it intermittently). Resolved: 14 creates through a no-retry store at the route (red 4/4 on the old store: 3×201, 11×500; now ten 201 and four 409); task 2.9. This touches `server/src/routers/**` (noted in Impact).
- [x] [minor] Task 2.4's evidence was green only (no test fails if `createdAt` is read before the queue). Resolved: a clock advanced while the create is queued (old store: 12:00, fixed: 13:00); task 2.10.
- [x] [minor] The store constructor now takes the concrete `PostgresCatalogDb` (for `txTimeoutMs`) instead of the port `CatalogRoot`. Declined: internal type, single construction site (`config.ts:193`), ports and `CatalogDb` contracts unchanged.
- [x] [minor] After a transaction timeout the connection is cancelled without a confirmed ROLLBACK, so the next queued create can meet the old backend's advisory lock and take one 40001 retry. Declined: bounded, pre-existing adapter behaviour.
- [x] [minor] Head of line: a create behind slow creates can time out in the queue although it would have succeeded. Declined: bounded and documented; correctness unaffected.
- [x] [minor] Verified sound: no HTTP change (201/409 unchanged; timeouts and exhausted retries stay the generic 500); FIFO order; map entry removed when the last create settles; a create cannot both time out and insert; the slot is released on throw, timeout and retry; the cap holds; tests fail without the queue (40001 under `maxTries: 1`) and without the deadline.
