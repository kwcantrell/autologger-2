# Panel: playlist-import-autogenerate
Tier: 2 · Reviewers: assumption tester, failure and abuse, scope and simplicity · Date: 2026-11-12

- [x] [major] The up-front `blocked` check does nothing for the common first import into an empty show (and for a show over 1000 sessions): the preview resolves the scope first and answers `400 No sessions to process.` / `A batch job can process at most 1000 sessions.` before it computes `blocked`, so the box never warns before hours of importing. Evidence: `grep -n "if (r.sessions.length === 0)\|blocked: await blockedFor" server/src/autogenerate/service.ts` -> `141:` (400 return) before `165: blocked: await blockedFor(p, steps)`. Resolved: when the preview does not answer `200`, the modal derives the verdict from the existing `GET /api/me/providers` (already read by Settings → Advanced through `useProviders`, fixture-checked) in the start route's order, mirroring `resolveLlmRoute` (no row; keyless `claude-cli` only while `claude_cli_allowed`) and `run_features_allowed`; no contract change. Residuals stated: an undecryptable saved key, and the dev-only `PROVIDER_DEV_MODE` Deepgram fallback (a false block on dev stacks); the confirm says providers are checked again when the import ends (spec "Up-front check" steps 1-3 and scenario "An empty show is still checked before importing"; design D6, A13-A16; tasks 1.1 `blockedFromProviders`, 4.1, 5.1).
- [x] [major] The ADDED requirement disables Start Import in cases where the in-flight `youtube-playlist-import` MODIFIED "Batch Import modal layout and actions" says it SHALL be enabled ("enabled when a show is selected, no run is in progress, and at least one of these is ready"), so the two specs contradict. Evidence: the enable rule and scenario "A playlist alone enables Start Import" in that requirement versus this delta's "Start Import SHALL also be disabled while the checkbox is ticked and no step is ticked … or more than 1000". Resolved: the delta now MODIFIES "Batch Import modal layout and actions", restating the whole requirement as synced on main by the archive (PR #144) with the narrowed enable rule (step ticked, at most 1000 checked, no blocked verdict while the box is ticked), the group's place, the confirm before the run and the autogenerate start after the log part; "A playlist alone enables Start Import" kept (box unticked) plus new scenario "Autogenerate options can disable Start Import"; the ADDED requirement points to it instead of restating the rule.
- [x] [major] Tier 1 understates the risk: one confirm commits unattended paid spend on the user's providers (up to 1000 × 4 runs) that starts hours later with no second prompt, and the change fixes an ordering guarantee (start only after every part, design D3) and a no-retry rule for a start with an unknown outcome (design D5); risk-tier says pick the higher tier when unsure. Evidence: `.claude/skills/risk-tier/SKILL.md` tier 2 list ("Concurrency, locking, retries or ordering guarantees"; "When unsure between two tiers, pick the higher one"). Resolved: raised to Tier 2 by the orchestrator and owner (proposal Tier and Tier reason); the remaining two tier-2 reviewers run after these fixes; tasks add the consistency read (5.3).
- [x] [major] "Qualifying sessions" counts a retry into this import's own unfinished session from an earlier run, which owner decision 1 ("created AND attached audio to") does not clearly allow; the design left it as open question Q1 although it changes the spec. Evidence: design D2 and the former Open question Q1. Resolved: owner decided and confirmed 2026-11-12 to include such a session; recorded as proposal owner decision 5, Q1 closed in design (D2, Open Questions), the spec sentence names it and a scenario "A retried session from an earlier run qualifies" plus task 4.1 test it.

## Failure and abuse, scope and simplicity (2026-11-12)

- [x] [major] (scope) The provider-status fallback hard-blocks Start Import on a guess: it cannot see an undecryptable key or the `PROVIDER_DEV_MODE` Deepgram fallback, so on a dev stack an empty show with Transcripts ticked is blocked although the start would accept it, and the import itself is held hostage by an autogenerate guess. Evidence: design D6 residuals; `sed -n 35,38p server/src/auth/providerResolve.ts` -> `if (env.config.PROVIDER_DEV_MODE === true && fallback) { return { apiKey: fallback, … } }`. Resolved: only the preview's exact `200` `blocked` for the current selection hard-disables Start Import; the provider-derived result (preview `400` for an empty or oversized show) is a non-blocking warning followed by "Your providers are checked again when the import ends." (spec "Up-front check" steps 2-3, scenario "An empty show only warns"; design D6; tasks 4.1 fallback-warning case, 5.1).
- [x] [major] (failure) Start Import is enabled while the up-front check is pending or stale: the preview hook keeps the previous answer as placeholder data, so after a step change a click rides on the old `blocked: null`; and the verdict is not looked at again after the confirm, so a block that arrives while the confirm is open still starts hours of import. Evidence: `grep -n "placeholderData: keepPreviousData" web/src/api/hooks/useAutogenerateJobs.ts` -> `45:`; design D6 (no re-check). Resolved: an answer counts only for the current show, steps and wiki mode and never as placeholder data; while pending Start Import is disabled ("Checking your providers…"); after the confirm the current verdict is read again and a block runs nothing (spec "Up-front check" step 1, "Confirm", scenarios "Start Import waits for the current check" and "A block that arrives during the confirm stops the run"; design D6; task 4.1 pending, stale and late-block cases).
- [x] [major] (scope) The ticked state outlives the group: after a new link, a failed listing, or unchecking every entry, a hidden or empty-playlist checkbox still narrows Start Import and prompts the confirm for a folder-only or logs-only run. Evidence: the MODIFIED enable rule ("while Autogenerate after import is ticked") had no condition on the group being shown or on checked entries. Resolved: "armed" = group shown, ticked and at least one entry checked; only then do the narrowing, the up-front check, the confirm and the id collection apply; hiding the group unticks it and resets the options (MODIFIED enable rule and scenario "A ticked box with no checked entry does not narrow Start Import"; ADDED "The group" and scenario "Loading another link unticks the box"; design D11; task 4.1 arming case).
- [x] [major] (failure) An interrupted run loses already-imported videos: an overlay click or Escape during an hours-long run closes the modal (abort), and on the rerun the videos whose audio the server finished meanwhile are skipped as "already in system", so they never reach any job. Evidence: `grep -n "onOpenChange={(o) => !o && handleClose()}" web/src/pages/index/components/BatchImportModal.tsx` -> `286:` (no `closeOnOverlayClick`); `sed -n 218,221p web/src/pages/index/batchImport/playlistRunner.ts` -> a remembered own session with segments falls to `log(formatSkippedLine(name)); return 'done';`. Resolved: during a run the modal passes `closeOnOverlayClick={false}` and ignores `onOpenChange(false)` (Escape); Close still aborts (MODIFIED rule and scenario "Escape does not interrupt a run"; design D13); this import's remembered own session that has audio from an earlier interrupted run qualifies on the rerun and is then forgotten (ADDED "Qualifying sessions" second bullet, scenario "An interrupted earlier run's import qualifies on the rerun"; design D2; tasks 2.1, 2.2); the no-session line now reads "no video was imported by this import". The owner confirmed this qualifying extension on 2026-11-12 (proposal decision 5).
- [x] [major] (failure) Account switch: the confirm's spend authority outlives the session. If the user signs out and another user signs in in the same browser during the run, the end-of-run start spends the second user's providers under the first user's confirm. Evidence: design D5 (no user check before the preview); the modal stays mounted across a profile change. Resolved: the user id is recorded at the confirm and the profile is read before the end-of-run preview; a different user gets "Autogenerate not started: you are signed in as a different user than the one who confirmed." and no request (spec "End-of-run start" step 2, scenario "Another account does not inherit the confirm"; design D12, D5; tasks 3.1, 4.1).
- [x] [major] (failure) One deleted or hidden session sinks the whole job: an id scope answers `404 Session not found` for any missing id, and the no-retry rule then drops every other imported video. Evidence: `grep -n "rows.length !== ids.length" packages/catalog/src/autogenerateStore.ts` -> `814: if (rows.length !== ids.length) return { ok: false, reason: 'session-not-found' };`. Resolved: one re-scope: on that `404` from preview or start the modal re-reads the run's show's sessions (re-aligning the active show), drops missing ids, logs "Autogenerate: left out <k> imported session(s) that no longer exist." and runs preview → start once over the rest; a second `404` ends it; stated as a re-scope (a smaller set after a refusal that wrote nothing), not a retry (spec "One re-scope on 404", scenario "A deleted session is left out once"; design D4, D5; task 3.1).

Minor, not a finding (scope reviewer, done anyway): `useDebounced` joins the D8 extraction, and the end-of-run start calls fetch functions extracted from the existing hooks instead of adding `apiFetch` sites (design D8 "Fetch functions"; tasks 1.2, 3.2, 3.3).
