# Panel: byo-ai-providers
Tier: 2 · Reviewers: assumption tester, failure and abuse, scope and simplicity · Date: 2026-10-08

- [x] [critical] A stolen session can exfiltrate the write-only key. A `PUT /api/me/providers/llm` that changes `base_url` but omits `api_key` keeps the stored key, and `POST …/llm/test` then sends `Authorization: Bearer <victim key>` to the attacker's host. Every future model call has the same hole, and the AAD (`userId\0kind`) does not bind the destination. Evidence: design D4 "PUT with no api_key … keeps its key columns"; api-contract-freeze delta "when absent on a replace, the stored key is kept". Resolved: a base URL origin change needs a new key (`422` otherwise), and the origin is in the AAD; provider-credentials "A stored key is bound to its destination", design D2, D4.
- [x] [major] A keep-key `PUT` is read-then-upsert, so it can write a just-deleted or just-rotated key's ciphertext back. Evidence: design D1 (`get` then `upsert`), D4. Resolved: the keep-key path is one `UPDATE` with no prior read that never writes key columns, and zero rows answers `422`; design D1 `updateKeepingKey`, task 2.2.
- [x] [major] A key containing CR, LF or another control character is stored, and undici then throws `TypeError: Headers.append: "Token sk_secret\nX" is an invalid header value.`, which carries the whole key. The outbound and test code have no rule against logging or forwarding error messages. Evidence: Node 24 `fetch` with a header holding `\n`; api-contract-freeze PUT validation rejects only NUL; design D5 result mapping. Resolved: keys and models are printable ASCII without spaces, and provider errors are classified, never logged or forwarded; provider-credentials, design D5, tasks 4.1, 4.2.
- [x] [major] A wrong `PROVIDER_KEYS_SECRET` boots cleanly while every row fails to decrypt. GET still shows the credentials as set, the profile says configured, the test result is undefined, and a keep-key save preserves dead ciphertext. Evidence: design D2 (boot checks length only), D3 (profile without decrypting). Resolved: a check value in `kv` makes boot refuse a mismatched secret, and the test reports an undecryptable key as needing re-entry; the profile field is cut; design D2, task 3.3.
- [x] [major] Every SSRF protection and the no-fallback rule switch on `NODE_ENV === 'production'`, so an unset or misspelled `NODE_ENV` turns them all off, and no `Config` field carries it. Evidence: `grep -n NODE_ENV server/src/node/config.ts packages/ports/src/config.ts server/src/env.ts` -> only `config.ts:146` (HOST); design D3, D5. Resolved: `Config.PROVIDER_DEV_MODE` is set at boot, true only for `NODE_ENV` `development` or `test`, so production mode is the default; provider-credentials "Development mode is explicit", design D3, task 3.2.
- [x] [major] The test route is an unthrottled egress and probe oracle for any signed-in user: Resolved (owner choice): 5 tests a minute per user, shared across processes (`429`); production-mode URLs are https on port 443 with no query or fragment; a refused host reads as unreachable; DNS is inside the 10 s timeout; design D4, D5.
  - any public host, port, path and query string;
  - a separate "not allowed" answer that reveals internal DNS names;
  - a `dns.lookup` the 10 s timeout doesn't bound;
  - no approved-user gate.

  Evidence: design D4 (only a per-process single-flight), D5 (save-time checks: scheme, userinfo, length).
- [x] [major] The web never shows the transcript-generate `503` detail. `useGatedGenerate` latches on any `503`, and `TranscribeFeed` hardcodes "needs `DEEPGRAM_API_KEY` … Reload this page after configuring it". The latch also survives saving a key. web-session-console "Honest capability gating on generation features" requires that copy, and no delta or task covers it, so the proposal's "no other control changes" is false. Evidence: `grep -rn "DEEPGRAM_API_KEY" --include=*.tsx web/src | grep -v test` -> `TranscribeFeed.tsx:306`, `:352`; `generateLatch.test.tsx` asserts the old copy. Resolved: a web-session-console delta; the copy names Settings → Advanced, and saving a key clears the latch; design D6, task 6.2.
- [x] [major] No core-ports-architecture delta, though the new system store needs a new reviewed system-binding reason and that requirement lists the reasons exhaustively, and a repository test refuses unlisted ones. Evidence: core-ports-architecture allowlisted reasons; design D1 "the system binding". Resolved: the core-ports-architecture delta adds the `provider-credentials` reason, and the allowlist test changes under D7 category 5.
- [x] [major] An unconditional secret check in `createBindings` breaks tests outside D7. Evidence: `grep -n "frameBus\|checkFrameBusSecret" server/src/node/config.ts` -> `69: options.frameBus === 'postgres' ? checkFrameBusSecret(…) : null`; `createBindings(` is also called by `config.test.ts`, `auth.int.test.ts`, `sessions.youtubeImport.int.test.ts`, `frameBus.int.test.ts`, `busProcesses.ts`, `startupPurge.test.ts`; `bootOrder.int.test.ts` asserts `catalog not ready` with no such secret. Resolved: the check runs only with the `providerKeys: 'required'` option that `main.ts` passes; other entry points get a per-process random secret; the two boot tests that spawn `main.ts` are D7 category 8.
- [x] [major] There is no evidence that `GET https://api.deepgram.com/v1/projects` is free and succeeds for a key scoped only to transcription. A scoped key may get `403`, which D5 maps to "rejected". Evidence: `curl -s -m 10 -w "\n%{http_code}" https://api.deepgram.com/v1/projects -H "Authorization: Token invalid_key_123"` -> `401` (a valid or scoped key was not testable). Resolved (owner choice): the test sends a 0.25 s silent clip to `/v1/listen` with the model, which proves transcription scope and the model; design D5.
- [x] [major] Users who aren't approved hit a dead end. The `503` tells them to add a key, and Advanced is open to every user, but after they save one, generation answers the approval `403`. The frozen order is the config `503`, then the `403`. Evidence: api-contract-freeze "Run features are limited to approved users"; web-ui-system delta "available to every signed-in user". Resolved (owner choice): the frozen order stays, and Advanced shows an approval note from `run_features_allowed` on `GET /api/me/providers`; web-ui-system delta.
- [x] [major] `PROVIDER_KEYS_SECRET` becomes a hard boot requirement, but local-container-environments gets no delta. Its OpenBao failure list makes compose refuse up front when a boot-required key is missing; without the delta, a missing secret crash-loops the `api` container. Evidence: local-container-environments OpenBao "Failures" list; `docker/scripts/compose-run.mjs`. Resolved: a local-container-environments delta, and `compose-run` refuses a stack without it; task 3.4.
- [x] [major] The profile `providers` field has no consumer in this change but would become permanently frozen surface and a read on every profile load. Evidence: design D6 uses `GET /api/me/providers`; the proposal's web scope. Resolved: cut.
- [x] [major] The per-user test single-flight `409` freezes a new status for little value: it is per process, and design D4 says a duplicate test costs one free request. Evidence: design D4. Resolved: cut, replaced by the cross-process rate limit (`429`).
- [x] [major] The tasks miss docs that become false or are promised: Resolved: tasks 3.4 and 5.3 name `docker/.env.example`, `docs/security.md` and every README gate statement.
  - `docker/.env.example:34` (`# DEEPGRAM_API_KEY=`);
  - `docs/security.md`, which records the `FRAME_BUS_SECRET` threat at lines 88-101 but nothing about the at-rest cipher or user-directed egress;
  - the README's global-gate statements at lines 61, 73, 130, 229, 245, 1107, 1263, 1448 and 1814.

  Evidence: tasks 3.2, 5.4.

## Re-panel (2026-10-08)
Delta: the revisions above. Reviewer: a fresh failure-and-abuse and scope reviewer. It found that the ticked resolutions close their findings, except the items below.

- [x] [major] Design D3 put `resolve` after the approval `403`, reversing the frozen order of the config `503` and then the `403`. Evidence: design D3; `server/src/routers/transcribe.ts:157-161`. Resolved: D3 now resolves in place of the env-key check, then `requireRunFeature`.
- [x] [major] `kv` has no atomic increment or insert-if-absent, so neither the rate limit nor the check value had a safe implementation. Evidence: `packages/ports/src/kvStore.ts` (get, put, delete, take, replaceIf, purgeExpired). Resolved: an atomic `takeTestSlot` `UPDATE … RETURNING` on the credential row, and a single-row `provider_key_check` table with `on conflict do nothing`; catalog-database delta, design D1, task 2.2.
- [x] [major] The spec's rolling minute and the design's fixed `<minute>` key disagreed, and the test would be flaky. Resolved: one window definition (it opens at the first test after the last one ended and lasts 60 s), on the injected Clock; provider-credentials, D1, task 2.2.
- [x] [major] The keep-key `UPDATE` compared an origin that wasn't stored, and its normalization was unspecified. Resolved: a stored normalized `base_origin` column, also used as the AAD, and `base_url` normalized before saving; catalog-database delta, D1, task 4.3.
