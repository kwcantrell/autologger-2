# event-generate-hardening — design

## Context

Three recorded PR#4-review residuals on the `events/generate` surface need contract
deltas (see `proposal.md`). Current mechanics that shape the design:

- The route (`server/src/routers/events.ts`, generate handler) runs a synchronous
  pre-spawn prologue: guard ladder → AI-slot acquire → (regenerate)
  `hub.deleteAutoGeneratedEvents()` → run-snapshot build → `driveAiTurn`. No `await`
  sits between the slot acquire and the turn registration, so nothing interleaves
  with the prologue; the per-session slot then serializes generate/chat/topics runs
  for the session until the turn ends.
- The prompt's message builder receives `existingEventsForGenerate(hub.exportEvents(),
  selectedCategoryIds)` — per-category lists of the session's current events (with an
  `isAuto` flag) so the model avoids duplicating events that already exist. Today
  regenerate deletes *before* this enumeration, so old auto rows never reach it.
- `SessionHub` RPC bodies are synchronous; every mutating RPC is transactional via
  `inTxn` with post-commit broadcast flushing (`event.changed`).
- The web derives the Generate All ↔ Regenerate All label from
  `useEvents(sessionId, { limit: WORKSPACE_EVENTS_LIMIT })` (2000, the server's max
  list clamp) — blind to auto rows past the clamp.
- `web-api-response-conformance` pins client types against captured fixtures in CI;
  the events list envelope is one of the pinned shapes (fixtures are regenerated
  outputs, never source).

## Goals / Non-Goals

**Goals:** truthful Regenerate labeling at any session size; regenerate that never
destroys the prior set before a replacement exists; bounded generate-body strings.

**Non-Goals:** see `proposal.md` (Generate All/Custom mechanics, pagination/clamp
changes, historic duplicate cleanup, menu redesign, other residuals).

## Decisions

### D1 — `has_auto_generated` lives on the events list envelope

Alternatives: (a) new field on `GET …/status`; (b) a dedicated endpoint; (c) raise
the clamp. Chosen: the events list envelope. The label's data source is already an
events query; the field rides the exact invalidation path that must refresh the
label (`event.changed` → events-prefix invalidation), so a regenerate/create flips
the label live with zero new plumbing. Status polling would add a second
freshness path; a dedicated endpoint is new surface for one boolean; raising the
clamp just moves the lie. Computed by the event store's SQL predicate; the
generate route keeps its JS `isAuto` predicate for the snapshot (gate ruling E3),
and the two are pinned equal by a parity unit test — two implementations, one
tested meaning.

### D2 — Delete-after-success via pre-spawn **id snapshot** (not run-tag delete)

Alternatives: (a) delete-by-tag — `create_event` already stamps every generated
row's metadata with `{auto_generated: true, auto_generate_run_id: <runId>}`
(fact-check claim 11), so success could delete auto rows whose
`auto_generate_run_id` differs from this run's; (b) delete-before (status quo).
Chosen: snapshot the ids of current `auto_generated` rows in the synchronous
prologue (after slot acquire), delete exactly those ids after `outcome.ok`. The
held per-session slot plus the synchronous prologue make the snapshot exact for
the run's own purposes — the only *server-stamped* writer of `auto_generated`
rows mid-run is the run itself (panel correction to fact-check claim 11: the
events POST passes arbitrary client metadata through, so clients CAN stamp the
flag at any time — but a mid-run client-stamped row merely survives the by-id
delete and is swept by the next regenerate's snapshot, so the safety claim
holds), whose rows are by definition not in the snapshot. Delete-by-tag would reach the same row set
but computes membership by re-parsing metadata at delete time; the id snapshot
fixes the delete set pre-spawn — deterministic, directly assertable in tests, and
no metadata parsing on the delete path. Either way a crashed process leaves both
sets intact (self-healing: the next regenerate snapshots old+partial rows together
and replaces both). **Gate ruling E1:** the delete is additionally gated on
`created > 0` — a clean CLI turn that created nothing keeps the prior set and
responds `200 { created: 0, cap_hit: false, deleted: 0 }` (destruction requires a
replacement; honors the topics precedent's keep-on-zero-output spirit while
staying a truthful 200). **Gate ruling E3:** the snapshot is derived
**route-side** from the prologue's existing `hub.exportEvents()` read using the
route's JS auto-predicate (the topics route's own shape) — no dedicated
store-side id-listing RPC; the exclusion set and delete set are the same array by
construction. The JS predicate and D1's SQL predicate are pinned equal by a
dedicated parity unit test.

### D3 — Snapshot rows are excluded from the existing-events enumeration AND the anchor basis

Without the prompt exclusion, delete-after-success is self-defeating: the prompt
would present the old auto rows as "existing", and the model — instructed to avoid
duplicates — would regenerate nothing. On regenerate, `existingEventsForGenerate`
receives the export minus the snapshot ids. **Panel extension (assumptions
reviewer):** the exclusion must be symmetric on the anchor side too —
`create_event` computes each new row's stored `wall_time_utc` via
`timecodeWallAnchors(hub.exportEvents())`, so under delete-after-success the
doomed rows would otherwise steer the replacement rows' persisted wall times
(destroying regenerate's cleansing property when the old rows carry bad
anchors). The snapshot ids therefore ride the run context and are filtered from
the anchor basis as well. Non-regenerate runs are byte-identical to today.

### D4 — `deleted` reports rows actually removed post-success

The bulk delete targets snapshot ids still present (`DELETE … WHERE event_id IN`,
one transaction, one `event.changed`). If an operator manually deleted an old auto
row mid-run, `deleted` shrinks accordingly — the count stays honest. A
zero-created success skips the delete entirely and reports `deleted: 0` (gate
ruling E1). The response field's name, type, and conditionality are unchanged.

### D5 — Bounds: `selection` ≤ 500 entries, `category_id` ≤ 200, `option_label` ≤ 200

Rationale: `category_id` matches `eventUpdateBodySchema.category`'s existing 200
cap (ids are UUIDs, 36 chars); `option_label` matches the settings **write path's
existing 200-char cap** on dropdown option labels (`validateCategoriesList`:
"Dropdown option text is too long" — fact-check claim 8), so no storable label can
ever be excluded by the bound; 500 selection entries exceeds any realistic
instruction-bearing set (the aggregate pre-spawn entry bound is configured far
lower). These are DoS-hardening bounds, not semantic limits; violations reuse the
existing malformed-body `400 {detail}` (no new detail string).

### D6 — Hub RPC: `deleteEventsByIds(ids)` replaces `deleteAutoGeneratedEvents()`

The predicate-based bulk delete has no remaining caller once the route deletes by
snapshot ids. Replace it (hub delegate + event-store method + tests) rather than
keeping dead internal API — hub RPCs are internal surface, not the frozen HTTP
contract. The new RPC: synchronous, `inTxn`, **chunked** `DELETE … WHERE event_id
IN (…)` statements of at most 500 ids inside the one transaction (panel, failure
reviewer: this repo's better-sqlite3 hard-fails at 32,767 bound variables, and
the snapshot is not bounded — an unchunked delete would turn a paid successful
run into a 500 and permanently wedge regeneration), one `event.changed`
broadcast when the total deleted count > 0 and none otherwise (parity with the
old RPC's `changes > 0` guard — WS emission semantics are frozen), returns the
deleted count. **The post-success delete call site MUST re-acquire the hub
(`getSessionHub(c, sessionId)`) after the multi-minute await — never reuse the
prologue's hub reference** (the registry evicts idle hubs mid-run; the route's
`finally` already re-acquires for the same reason). The auto-predicate itself
stays in the event store (shared by the snapshot read and D1's envelope flag).

### D7 — Web label reads `has_auto_generated` from the sheet's own page query

`EventLogSheet`'s label logic drops the row-scan of the workspace-wide query and
reads the new envelope field from its own (first-page) events query. The
workspace-wide subscription in the sheet REMAINS — the timeline-reveal page-growth
fix reads it for the id→index lookup — but the label no longer depends on it.

**Invariant note for future readers:** the per-session AI slot serializing runs is
what makes D2's snapshot exact and D3's exclusion safe — do not make the prologue
async or move the snapshot after an `await`. And on the far side of the run: the
post-success delete goes through a freshly re-acquired hub, never the prologue's
reference (D6) — the snapshot's *ids* survive a hub close/reopen (persistent
UUID PKs), the handle does not. (Same class as the repo's "SessionHub RPC bodies
are synchronous" invariant.)

## Risks / Trade-offs

- **Mid-run duplication visibility:** during a regenerate run, readers see old rows
  plus incoming new rows (both `auto_generated`). Accepted: transient, honest
  (nothing is destroyed yet), and the delta specs it. The pre-change behavior
  (window with *nothing*) was the worse UX and the data-loss path.
- **Failure leaves old + partial-new rows:** more rows than before the run, until
  the next successful regenerate. Accepted and spec'd; matches append-failure
  persistence semantics and is self-healing (D2).
- **Conformance fixtures:** the conformance check is deliberately
  additive-tolerant server-side; it fails in the OTHER direction — once the
  hand-written `EventsResponse` type gains `has_auto_generated`, the captured
  fixture must be re-captured or the assignability check stops compiling
  (fact-check claim 10). Type edit + fixture re-capture land together — called
  out in tasks.
- **Existing tests pinning delete-before ordering** (int tests asserting pre-guard
  400s delete nothing / delete-before-spawn) need re-pinning to the new ordering —
  test edits are part of the same phase as the behavior change, never a separate
  "fix the tests" pass.
- **Mid-run edit loss (new window):** old auto rows are PUT-editable for the whole
  run; the by-id delete then destroys the edit regardless of content (PUT keeps the
  row's id and `auto_generated` flag). Narrow window, no rescue path — accepted,
  and the regenerate confirm copy (updated in this change) is where the operator
  learns rows are doomed.
- **Client-spoofable predicate (pre-existing, recorded):** the events POST accepts
  arbitrary metadata, so any client can stamp `auto_generated: true` — flipping the
  label and marking its rows for the next regenerate's sweep. Not new surface (the
  old delete shared the predicate); recorded rather than silent.
- **`has_auto_generated` EXISTS cost:** worst case (no auto rows) scans the table's
  metadata JSON per events GET. Fine at this schema's scale; if it ever shows up in
  a perf pass, revision-keyed memoization or a maintained flag is available without
  a contract change.
- **Bounds are post-parse hardening, not DoS protection:** `c.req.text()` +
  `JSON.parse` still consume an arbitrary-size body before zod runs (true of every
  JSON route here — a global body limit is out of scope). The bounds cap what
  propagates into snapshot filtering, and give an honest 400.
- **Legacy over-long labels:** stored categories predating the current validator
  could theoretically carry a >200-char option label, whose Custom-selection entry
  would 400 until renamed — accepted residual (the route already defends against
  looser legacy JSON elsewhere).
- **Cross-run accumulation under chronic failure (gate ruling E2 — recorded
  residual):** each failed regenerate leaves ≤cap partial rows; nothing bounds the
  total across retries, and prompt size/per-run spend grow with the pile (each run
  individually bounded by `maxBudgetUsd`). Accepted without a new guard: the
  chunked delete removes the hard wedge, a later successful regenerate sweeps
  everything (old + all partials are in its snapshot), and manual deletion works
  meanwhile. Revisit only if a real deployment hits it.
