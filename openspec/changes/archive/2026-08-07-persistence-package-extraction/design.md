# persistence-package-extraction — Design

## Context

Step 2 of the modular-monolith campaign. Exploration (2026-08-07, this session) mapped
the extraction surface against live `main` (post `package-split-foundation`,
8e1c34e/e154312). Load-bearing facts (to be re-verified by the fact-check pass):

- `server/src/db/` production modules import **only** `@autologger/domain` and
  `@autologger/ports` — already package-pure. The `Catalog` facade is five `readonly`
  store fields + `init()`; ~67 public methods are on the stores (shows 4, studios 17,
  auth 30, sessionIndex 13, profile 3 public). `Catalog` takes a `CatalogDb` port — it
  has no `better-sqlite3` dependency. (Step 1's "~71-method" shorthand counted
  slightly high; corrected by the fact-check pass.)
- `server/src/session/` production modules import only `@autologger/*`,
  `better-sqlite3`, and `node:fs/os/path`. Outside the test-infrastructure imports
  (`test/fakeCore`, `test/fakeClock`, `test/harness`, `test/helpers` — enumerated and
  dispositioned in D2), the **only** session→server edge is test-only:
  `eventStore.test.ts` imports `isAutoGeneratedMetadataJson` from `routers/events`
  (the writer-predicate/SQL-predicate agreement test).
- `SessionRuntime` (the port in the core-ports ledger) is declared in
  `session/sessionCore.ts`, consumed by the stores and `server/src/test/fakeCore.ts`.
- Storage adapters: `node/blobStore.ts` (node builtins + ports only; exports
  `InvalidRangeError`, mapped to 416 by `instanceof` at `app.ts` and
  `routers/audio.ts`), `node/kvStore.ts` (better-sqlite3 `Database` + ports +
  `systemClock` **default param** — the composition root already passes the clock
  explicitly at `config.ts`), `node/catalogStore.ts` (the `CatalogDb` impl),
  `node/migrate.ts` (`openCatalogDb` + directory-generic `applyMigrations`).
  `config.ts` resolves `MIGRATIONS_DIR` as `../db/migrations` via `import.meta.url`.
- Consumers to rewrite: 14 production server files import `session/` (routers, aiV2,
  logImport, node/generateTranscript, appEnv, test helpers), 11 import `db/`, 2 import
  `node/blobStore` (`InvalidRangeError`) — ~29 distinct staying-in-server files get
  import rewrites; ~50 files physically move. `test/fakeCore.ts` imports
  `sqliteSessionSql`, `SessionCore`, `SessionRuntime` from session modules;
  `node/kvStore.test.ts` and `node/presence.test.ts` use shared test fakes.
- `SessionHub` has 55 public members (51 methods + `hasArmedAlarm`/`socketCount`
  getters + the `lastTouchedMs` field + constructor), including mutable coordination
  state that only the registry (same module) should touch — the narrowing value of a
  facade interface is real, not ceremonial.
- **`Catalog` is constructed per request in `middleware/auth.ts`** (`new
  Catalog(c.env.ports.catalog)` + `init()`, which refreshes the studio registry's
  per-instance snapshot once per request) — `config.ts` never constructs a `Catalog`.
  Retiring the concrete-class allowance therefore needs a sanctioned construction
  path for middleware, not just type rewrites (panel finding; see D3).
- **web-docs is a live consumer of the moved modules** (panel finding):
  `web-docs/src/lib/erSchema.ts` imports `node/migrate`, `session/SessionHub`, and
  `session/sessionCore` by relative path; `erSchema.test.ts` and `check.ts` hard-code
  `server/src/db/migrations`; `scripts/snapshot.test.ts` asserts live extraction
  edges into `node`/`session`; `extractImports.ts` hard-enumerates the workspace
  list, so three new packages need extractor entries before their files are walked.
  web-docs runs in root typecheck and root test — its rewrites are per-phase work,
  not phase-7 polish.
- The existing boundary test hardcodes the three L0 edges in `ALLOWED_LAYER_EDGES`,
  carries a **positive** `aiV2 → session` directory-edge pin, and lists `db`/`session`
  in `SERVER_SRC_LAYER_DIRS` — so each extraction phase must carry its own minimal
  boundary-test delta or its gate goes red (panel finding; see D6).
- `middleware/auth.ts` aside, the only production constructions of the concretes are
  the registry in `config.ts` and hubs inside the registry (same module).
- Step-1 invariants in force: boundary enforcement is
  `packageBoundaries.repo.test.ts` (extend, never fork); per-project `tsc --noEmit`
  (no `tsc -b`); per-package `vitest run` scripts chained from the root `test`
  script; `systemClock` lives in `server/src/node/`; `SessionHub.DEFAULT_CLOCK` stays
  a local literal; zod stays a contract peerDependency; appEnv is composition, not a
  barrel.

## Goals / Non-Goals

**Goals:**
- Extract `@autologger/session-core`, `@autologger/catalog`, `@autologger/storage` as
  L1 source-only sibling packages with test-enforced boundaries.
- Retire the appEnv concrete-class allowance: routers/middleware reach persistence
  through package-exported facade interfaces; the composition root is the sole
  production module naming concrete classes.
- Close step 1's third-party-specifier boundary-guard residual (now load-bearing:
  packages carry `better-sqlite3`).
- Keep every observable behavior identical (frozen contract; pure refactor).

**Non-Goals:**
- `presence` and `systemClock` stay in `server/src/node/`; `aiV2/aggregates.ts` stays
  put (web pins its path). No router surgery, no feature packages, no SessionToolPort,
  no Config slicing, no web split, no wire changes, no build step, no second process.

## Decisions

### D1 — Three sibling L1 packages; layer graph and allowed edges

`session-core → {domain, contract, ports}`, `catalog → {domain, ports}`,
`storage → ports`. No L1→L1 edges: SessionHub opens its own per-session `Database`
directly (it does not use storage's adapters), and `catalog` speaks `CatalogDb` (the
port), not the storage implementation. The server app composes all three.

*Alternatives:* one `persistence` mega-package (recreates a god-module one level up;
loses the catalog package's zero-better-sqlite3 property and the storage package's
clean adapter framing); making `catalog` depend on `storage` (inverts the ports
discipline — catalog consumes the `CatalogDb` interface precisely so it doesn't know
the driver).

### D2 — Package contents and what deliberately stays behind

- **session-core**: all `server/src/session/*.ts` production modules (SessionHub +
  registry, sessionCore + `SessionRuntime`, audio/dashboard/event/lease/topic/
  transcript/transport stores, eventAnchors, audioSeamParts, storeHelpers), their
  colocated unit tests, plus the `fakeRuntime`/fake-clock test helpers those unit
  tests need (moved into the package as non-exported test infrastructure).
  `DEFAULT_CLOCK` remains a local literal in the hub module (step-1 invariant — moving
  to a package makes importing `node/systemClock` structurally impossible, which is
  the point).
- **catalog**: all `server/src/db/*.ts` production modules + `db/migrations/*.sql`.
  The package exports its migrations directory path (resolved via `import.meta.url`
  inside the package) as a constant.
- **storage**: `blobStore.ts`, `kvStore.ts`, `catalogStore.ts`, `migrate.ts` + their
  unit tests. `KvStore`'s `clock` parameter becomes **required** (the `systemClock`
  default import is the only thing binding these files to `server/src`; the
  composition root already passes the clock explicitly, so only test call sites
  change).
- **stays in server**: `presence.ts` (in-memory, not persistence), `systemClock.ts`
  (composition root's sanctioned `Date.now()` site), all `*.int.test.ts` files (they
  import the app harness / run under `setup.int.ts` — a package importing
  `server/src/test` would be an upward edge), `test/harness.ts` / `test/helpers.ts` /
  the server-side remnant of `fakeCore` if any server test still needs it.
  Session/db int tests relocate to **`server/src/test/`** (named destination — no
  husk directories; the tiers are glob-based so location within `server/src` is
  free; imports point at the packages; tier and `setup.int.ts` wiring untouched).
- **`migrate.test.ts` splits at the move** (panel finding): its ordering/idempotency/
  interrupted-run coverage is rewritten against **synthetic fixture `.sql` files
  inside the storage package** (it currently resolves the real migrations via
  `process.cwd()` and asserts the five real filenames — as-is it breaks in a
  package cwd, and pointing it at the real set would mint the exact storage→catalog
  coupling D7 forbids). The "real ordered set applies" assertion is owned by the
  fresh-`DATA_DIR` integration scenario (catalog side).

*Alternatives:* moving int tests into packages (forces packages to depend on the app
harness — upward edge, rejected); leaving unit tests in server (packages ship with no
tests, violating the per-package vitest-project mechanics from step 1).

### D3 — Facade interfaces live in the packages, not in `@autologger/ports`

`session-core` exports the hub facade interface (the RPC surface routers/tools use)
and a registry facade; `catalog` exports the `Catalog` facade interface (five
store-interface fields + `init()`), the five store interfaces, and a
**`createCatalog(db: CatalogDb)` factory** returning the facade type. Membership
criterion (normative in the delta): a member is on a facade iff it is reached through
`Ports.sessions`/`Variables.catalog` by at least one consumer outside the package —
which makes the registry facade exactly `get`/`evictIdle`/`startSweeper` (`main.ts`
calls `startSweeper` through `ports.sessions`; int tests reach `evictIdle` the same
way; `closeAll` is composition-root-only and stays off). Facade members are authored
as **property-style function types**, not method syntax: the panel empirically showed
method-syntax `implements` is bivariant in parameters (a concrete method that narrows
a parameter type still compiles), while property-style members are checked
contravariantly under `strictFunctionTypes` — with ~120 signatures being authored
once, the style choice is what makes "drift fails tsc" actually true. Concrete
classes declare `implements`. `appEnv.ts` types `Ports.sessions` and
`Variables.catalog` with these interfaces and imports **no concrete class**;
`node/config.ts` (composition root) constructs the registry; **`middleware/auth.ts`
constructs the per-request catalog via the factory** — the construct-then-`init()`
per-request lifecycle (request-scoped studio-registry snapshot isolation) is
preserved exactly, because hoisting `Catalog` to a startup singleton would let a
concurrent registry refresh mutate state under an in-flight request's awaits (an
observable isolation change on a frozen-contract-adjacent path, rejected).

Why not ports/L0: the step-1 panel proved facades-at-L0 jointly unsatisfiable — the
interfaces' parameter/return types are the stores' row and meta types; forcing them to
L0 drags most of the session package's type surface into `ports`. Colocated interfaces
give the same narrowing with zero type-migration churn: the package is already the
importable home of those types.

Narrowing is the point, not substitutability: interface members are the class's
*consumer-facing* surface; coordination internals (`lastTouchedMs`, `close`,
`socketCount` bookkeeping fields) stay off the interface, so `Ports.sessions` /
`Variables.catalog` structurally cannot reach them. Where a test legitimately needs
a concrete (constructing a registry over a temp dir), it imports the class from the
package explicitly — tests are exempt from the interface-only rule, production code
is not.

*Alternatives:* `Omit<>`-derived types over the classes (no independent statement of
the intended surface — the "interface" silently tracks whatever the class grows, which
defeats the audit-surface purpose that D5-of-step-1 established); facades in ports
(disproven, above); skipping interfaces because packages make the classes importable
anyway (leaves `lastTouchedMs`-style internals reachable from every router and keeps
the residual open — the campaign's stated point of this step). For the catalog
construction path: a startup singleton + per-request `init()` (rejected — isolation
semantics change, above); a factory field on `Ports` (rejected — changes the `Ports`
shape for what one middleware needs; the package factory is the narrower seam).
Durability: the interface-only rule is enforced by the boundary repo test (a
production file under `server/src` other than `node/config.ts` importing the concrete
identifiers from the two packages fails it — tests exempt), so the retirement cannot
silently un-retire with green gates.

### D4 — `isAutoGeneratedMetadataJson` moves to `@autologger/domain`

It is a pure JSON predicate (no zod, no wire shape — domain by the D9-of-step-1
discriminator) that two parties must agree on: the writer/reader in `routers/events.ts`
and the SQL predicate in `eventStore.ts` (whose test imports it today, creating the
only session→server edge). Both sides import it from `domain`; the agreement test
moves into the session-core package with `eventStore`'s other unit tests.

*Alternatives:* duplicating the predicate in the package test (the agreement test then
asserts agreement with a copy — worthless); leaving that one test in server (splits
`eventStore`'s test file across workspaces to dodge a one-function move).

### D5 — `better-sqlite3` as peerDependency of session-core and storage

Same reasoning as step 1's zod decision, with higher stakes: a second copy is not just
nominal-identity drift but a second **native** binding. The server workspace remains
the installing dependency (web-docs's own devDependency declaration dedupes to the
same resolved copy); both packages declare a peer range compatible with the server's.
Gates: `npm ls better-sqlite3` single-copy check alongside the existing zod check, and
the boundary test's new third-party-specifier assertion (D6) proves every package
declares what it imports.

*Alternatives:* regular dependency in each package (npm may still dedupe, but nothing
*guarantees* it across version drift — exactly the silent failure D8-of-step-1
documented for zod, and a native-module duplicate can break at install/ABI level);
hoisting to the root manifest (obscures ownership; the server is the runtime owner).

### D6 — Boundary test extension: L1 entries + third-party bare-specifier check

`packageBoundaries.repo.test.ts` (never a parallel walker) is extended
**incrementally, per extraction phase** — the panel showed the existing test fails
each extraction gate otherwise (`ALLOWED_LAYER_EDGES` holds only the three L0 edges;
a positive `aiV2 → session` directory pin and the `db`/`session` entries in
`SERVER_SRC_LAYER_DIRS` go stale in phase 4). So: each extraction phase's commit adds
that package's allowed edges; the session-core phase also retires the
`aiV2 → session` positive pin (the edge becomes a bare-specifier package import the
directory walker correctly no longer sees), prunes `db`/`session` from the server
directory list, restates which positive pins remain (`node → auth` survives), and
updates the stale `eventStore.test.ts → routers/events` scope comment killed by D4.
The dedicated enforcement phase then adds what is genuinely new: the no-L1→L1-sibling
assertion; the third-party bare-specifier check — every third-party bare specifier in
a package's **production** source (`*.test.ts` files and each package's declared
test-infrastructure files, named in a per-package list inside the boundary test —
reviewed, not improvised — are exempt and may use devDependencies like vitest) must
appear in that package's manifest (`dependencies`/`peerDependencies`); and the
interface-only assertion from D3 (concrete persistence identifiers importable only by
`node/config.ts` among `server/src` production files). New negative cases (undeclared
third-party specifier; L1→L1 import; non-composition-root concrete import) are
demonstrated once during implementation and recorded in the apply ledger, matching
the existing demonstrated-violation discipline.

*Alternatives:* eslint-plugin-import/dependency-cruiser (new toolchain for what an
existing owned test does); deferring the third-party check again (it was tolerable
when packages had zero/peer-only third-party imports; session-core and storage now
import `better-sqlite3` by name, so the gap is live); keeping all boundary-test edits
in one late phase (empirically red gates in phases 2–4, forcing off-plan edits into
mechanical-move commits).

### D7 — Migrations: `.sql` owned by catalog, migrator stays in storage

`@autologger/catalog` owns `migrations/*.sql` (schema and stores evolve together) and
exports the resolved directory path; `@autologger/storage` owns the directory-generic
`openCatalogDb`/`applyMigrations`. `config.ts` wires them:
`applyMigrations(db, catalogMigrationsDir)`. Behavior byte-identical (same files, same
ordering, same `_migrations` bookkeeping).

*Alternatives:* migrator into catalog (gives catalog a better-sqlite3 dependency it
otherwise doesn't need, spoiling its port-pure property); `.sql` into storage (storage
would own the catalog *schema* while catalog owns the queries against it — the
coupling lands in the wrong package).

### D8 — Toolchain wiring repeats step-1 mechanics verbatim

Per-package `tsconfig.json` + root `typecheck` additions (plain `tsc --noEmit`, no
`-b`, no composite); test wiring follows the **existing step-1 mechanism exactly** —
each package carries its own `vitest run` script and the root `test` script chains it
via `npm run test -w packages/<name>` (there is deliberately no root vitest
"projects" config; server's `vitest.config.ts` keeps its two-tier `test.projects`
untouched, `fixtures:capture --project` selector untouched); `biome.json` already
covers `packages/**` (verify, don't re-add); per-package
deliberately-failing-test execution proof repeated for the three new packages and
recorded in the apply ledger. The `npm ls` single-copy gates (zod, better-sqlite3)
are **JSON-parsed properties** (exactly one resolved copy in `npm ls <dep> --json`),
not exit-code checks — `npm ls zod` already exits 1 on today's main from an unrelated
`@anthropic-ai/claude-agent-sdk` peer-range complaint (`zod ^4.0.0` wanted) while
exactly one copy resolves; that environmental fact is recorded in the ledger, not
"fixed" by touching version pins. The gates are point-in-time ledger evidence; the
**continuous** protection against dual-instance regressions is the always-running
integration pins (422/400/416/dashboard-422) — do not delete an int pin on the theory
that `npm ls` covers it.

### D9 — web-docs co-migration is per-phase work, not phase-7 polish

`web-docs/src/lib/erSchema.ts` production-imports `node/migrate`,
`session/SessionHub`, and `session/sessionCore`; `erSchema.test.ts` and
`scripts/check.ts` hard-code `server/src/db/migrations`; `scripts/snapshot.test.ts`
asserts live extraction edges into the moving directories; and
`extractImports.ts` hard-enumerates the workspace list, so new packages are invisible
to the extractor until entries are added. Since web-docs is in root typecheck and
root test, each extraction phase carries its web-docs rewrites in the same commit as
the server rewrites (erSchema's migrations-dir caller switches to the catalog
package's exported constant — dogfooding D7), and the extractor gains the three
package entries + model components + regenerated snapshot as the phases land (with
final per-edge attribution review in the docs phase).

*Alternatives:* deferring all web-docs work to phase 7 (empirically red gates at
phases 2–4); excluding web-docs from root gates during the branch (hides exactly the
drift the atlas exists to gate).

## Invariants a future reader must not "helpfully" undo

- All step-1 invariants remain in force (single process; hub RPCs synchronous +
  transactional; `create_event` handler zero-await; no permanent re-export shims;
  ports ships no runtime values; zod stays a contract peer).
- `DEFAULT_CLOCK` in the hub module stays a local literal even now that the module
  lives in a package — importing `systemClock` from the package is impossible by
  construction; do not "fix" that by moving `systemClock` into a package.
- `appEnv.ts` names **zero** concrete persistence classes after this change — do not
  reintroduce a concrete type "temporarily" for a new field; extend the facade
  interfaces instead.
- The facade interfaces are exact-surface narrowings — do not add passthroughs that
  return concrete handles (no member returning the class, a store class, the
  registry, or the raw `Database`); the delta pins this with a negative scenario.
- Facade members stay **property-style function types** — converting them to method
  syntax re-opens the bivariant-parameter hole the panel demonstrated (a concrete
  method narrowing a parameter type compiles silently under method syntax).
- `createCatalog` is the sanctioned non-composition-root construction path, and the
  per-request construct + `init()` lifecycle in `middleware/auth.ts` is load-bearing
  (request-scoped studio-registry snapshot isolation) — do not "optimize" it into a
  startup singleton.
- `catalog` has no `better-sqlite3` dependency — it speaks `CatalogDb`. A convenience
  import of the driver into catalog collapses the port seam.
- L1 packages are siblings — a session-core→storage or catalog→storage import is a
  layering bug even when it would compile.
- Int tests stay in `server/src/` — packages never import the app harness.

## Risks / Trade-offs

- [~120 mechanical interface signatures could drift from intent during extraction] →
  `implements` makes drift a compile error; the interfaces are reviewed as the
  semantic commits, separate from the wide `git mv`/import-rewrite commits (step-1
  diff-hygiene rule).
- [Wide move diff masks semantic edits] → same mitigation as step 1: mechanical moves
  and import rewrites land as their own commits; semantic edits (interfaces, appEnv,
  KvStore signature, migrations wiring, boundary test) land narrow.
- [Native-module duplication via peer-range drift] → `npm ls better-sqlite3` gate +
  boundary manifest check (D5/D6).
- [Un-covered move breakage: `import.meta.url` migration-path resolution inside a
  package] → the vitest path is covered by the fresh-`DATA_DIR` integration scenario
  (real composition root) at the phase-3 gate; the tsx path is covered at the same
  gate by the `npm run start` fresh-`DATA_DIR` boot (next row) — neither deferred to
  e2e.
- [Test-helper shuffle (fakeCore/fakeClock) leaves a server test orphaned] → the move
  task enumerates all `test/fakeCore`/`test/fakeClock` importers (session unit tests,
  `kvStore.test.ts`, `presence.test.ts`) and the phase gate is the full root test run.
- [Dual-module-instance during the move window for `instanceof`-mapped classes —
  `InvalidRangeError` (416) in the storage phase, `DashboardValidationError`/
  `DashboardBoundsError` (422) in the session-core phase] → same-commit move + import
  rewrite (no shim window) for **every** `instanceof`-mapped class exported by a
  moving module; the 416 and dashboard-422 paths are pinned by integration scenarios
  (the `DashboardBoundsError` arm is wire-unreachable defensive code — accepted
  residual, covered by the single-module-instance property, not a wire pin).
- [`import.meta.url` migrations-path resolution under **tsx** is only proven by e2e
  at the end of the branch; the phase-3 integration scenario proves vitest] → the
  phase-3 gate additionally boots `npm run start` once against a fresh `DATA_DIR`
  (cheap, direct proof of the tsx path at the phase where the risk lands).
- **Residual (carried, unchanged owner):** `Config` stays one 31-field interface at L0
  (feature-package changes); `logImport/jobStore.ts` `pruneJobs` `Date.now()` TTL
  (future log-import cleanup); store-vs-delegate enforcement gap.
- **Residual (new, accepted):** the facade interfaces are hand-maintained parallel
  declarations; `implements` catches removals/signature drift but not a *new* public
  member added to the class and deliberately left off the interface — that asymmetry
  is the feature (narrowing), but nothing mechanically distinguishes "intentionally
  internal" from "forgot to expose"; review carries it.

## Migration Plan

Phased within one change, each phase green (`npm test` + `npm run typecheck`):
storage extraction → catalog extraction (+ migrations wiring) → session-core
extraction (+ domain predicate move) → facade interfaces + appEnv retirement →
boundary/toolchain extensions + negative-case demonstrations → atlas/docs + full
gates (`npm run docs:check`). Pure refactor: rollback at any phase boundary is
`git revert` of that phase's commits, no data or contract consequences.

## Open Questions

- Facade interface naming (`SessionHubFacade` vs `SessionHubApi` vs role-named like
  `SessionRpc`): cosmetic, settle at gate or first implement task; the spec pins the
  semantics, not the identifier.
- Whether `fakeClock` (needed by session-core tests, storage tests, and remaining
  server tests) is duplicated as tiny per-package test fakes or becomes a shared
  dev-only test utility — current lean: keep one copy in the package that uses it
  most and let server keep its own existing copy only if still referenced; decide at
  the test-move task with the importer inventory in hand (panel scope reviewer
  endorsed deferring: the helper is 22 lines, duplication is cheaper than any
  shared-test-utility construct).
