# Panel: session-tables
Tier: 2 · Reviewers: assumption tester, failure and abuse, scope and simplicity · Date: 2026-10-03

Reviewers report only critical and major findings (ADR 0024).

- [x] [major] The proposal declared that a `PUT …/events/:id` timecode beyond the 64-bit range now answers `500` (task 6.4 pinned it), but no api-contract-freeze delta covered it. Evidence: proposal.md "An event timecode beyond the 64-bit range fails the write"; tasks.md 6.4. Resolved: the case is unreachable (next finding), so the approver bullet and the 6.4 case are dropped.
- [x] [major] A11 was false. `eventUpdateBodySchema.timecode_hms` is exactly 8 characters and `frame_rate` is at most 120, so the largest total-frame value is about 4.32e9, which fits `bigint`. Evidence: `sed -n 77,82p packages/contract/src/schemas.ts` -> `timecode_hms: z.string().min(8).max(8)`; `node -e "console.log(9999*3600*120+59*60*120+59*120)"` -> `4319999880`. Resolved: A11 is rewritten as "every request- or user-supplied number bound into a session `bigint` is an in-range integer", with evidence per input.
- [x] [major] `POST /api/sessions/:id/audio/segments?recording_ordinal=<20+ digits>` answers `200` today (SQLite stored a real), but would fail Postgres `bigint` (`22003`/`22P02`) and answer `500`, an undeclared contract change. Evidence: audio.ts:196-197 `/^\d+$/.test(roRaw) ? Number(roRaw)`; bind test -> `22003 value "100000000000000000000" is out of range for type bigint`. Resolved: a `recording_ordinal` that is not `Number.isSafeInteger` is treated as missing (null), as non-digit input already is, so the response stays `200` (test first). The A11 audit found one more input: a sheet-log hour too large for a safe frame count makes `parseSheetTimecodeToSeconds` return null, so the row is dropped at fetch, as malformed rows already are. No contract delta is needed.
- [x] [major] Design open question 1 recommended folding the S4/S5 rolling re-check into `anchorImportedTake`, which the approved plan did not include, and the non-goals did not exclude it. Evidence: design.md OQ1; proposal.md non-goals list S1, S2, S7, S8 and S11 only. Resolved: (owner, 2026-10-03) fold it in. The plan of record is amended ("Owner decisions after the panel"). The anchor checks `is_rolling` after the row lock and refuses with each route's existing `409` and segment rollback (D7, tasks 5.2/5.7, core-ports and youtube-audio-import scenarios). S4/S5 are no longer carried.
- [x] [major] Hub calls would share the catalog's 5 transaction slots, with no limit per user. One member issuing about 35 heavy reads per second (a past-the-end events page costs about 145 ms on a 200k-event session; a 31,621-word transcript read costs about 40 ms) holds every slot, so sign-in, session create and other teams' writes time out with `500`. Evidence: design.md D2 "Connection budget: unchanged"; throwaway Postgres 17 benchmark -> `GET events offset-past-end, 200k events: ms 145`, `read 31k words ms 44.4`. Resolved: (owner, 2026-10-03) session calls get their own pool of 4 transaction slots, so the budget is 3 root + 5 tx + 4 session = 12 of the role's 20 per process. The integration role limit rises from 200 to 280. Risks states that one member can still saturate the session pool and slow other sessions, which then fail at the 10 s deadline (the rate-limit follow-up is already in the ADR's revisit list). Saturation tests (3.1, `poolIsolation.int.test.ts` in 5.2) show that `PUT /api/profile` and a session create's catalog transaction finish in under 1 s while every session slot is held.
- [x] [major] D2's guard refuses a hub call on another session from inside a hub transaction and rolls the outer transaction back. That contradicts the ADDED core-ports scenario "a call on another session's hub succeeds" and the moved test `SessionHub.concurrency.test.ts:170`. Evidence: scratch `nested.mts` -> `inner: CatalogTxMisuseError … outer: CatalogTxMisuseError` and `ROLLBACK`. Resolved: production never nests (A12). The requirement now says a hub call from inside any hub transaction is refused without deadlock: a same-hub call leaves the transaction usable, and a call on another session's hub fails the outer transaction (its own scenario). The test rewrite is on D12's allowed list (task 5.8).
- [x] [major] D12 did not cover the `fakeRuntime()` harness: 22 calls in 6 files and about 26 raw `core.db` statements depend on a root core that sends statements, broadcasts and alarms immediately, and that core goes away. Evidence: `grep -c "fakeRuntime()" packages/session-core/src/*.test.ts` -> sessionCore 16, eventStore 17, …; fakeCore.ts:30-60. Resolved: D12 names the replacement, `boundCoreOn(storage, sessionId)` in `server/src/test/session/boundCore.ts`. It runs each call in `storage.tx`, then flushes broadcasts and arms the alarm after commit. `rawRows` and `insertRaw` replace the raw statements. Moving those tests is on the allowed list (task 5.8).
- [x] [major] The hand-off to 7b-2 was understated. The seam carries no caller, because one storage object per hub is shared by every user. Under a user binding, the `FOR UPDATE` lock and the projection `UPDATE` run under `sessions_user_update`, so a writer without access gets 0 rows, which reads as `SessionNotFoundError`. Background writers have no caller at all. Evidence: design.md "7b-2 replaces this binding with the caller's"; catalog_policies.sql:205-207. Resolved: D2 and D14 (and the ADR text in task 7.2) list the constraints left for 7b-2: a per-call binding through the seam; the lock and projection under the caller's policy, with missing access distinct from a missing session; reviewed system bindings for the lease alarm, transcription, AI turns and the log-import job.

## Owner decisions (owner, 2026-10-03)
- S4/S5 rolling re-check: folded into 7b-1 (finding above).
- Session connections: own pool of 4 transaction slots (finding above).
- A projection failure fails the write. The api-contract-freeze requirement "Catalog mirror failures don't fail saved session changes" is retired by this change's delta.
- Stop rule: median `addEvent` above 5 ms, or the 31,621-word replace above 10 s, measured in the stack (dev app container to dev database).
