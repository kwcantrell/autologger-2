# Panel: drop-unused-supabase-services
Tier: 2 · Reviewers: assumption tester, failure and abuse, scope and simplicity · Date: 2026-10-08

- [x] [major] (scope) The MODIFIED container-deployment requirement kept the scenario title "Only the router is reachable from the host" while its new text says GoTrue is reachable from the host on `auth-egress`, so the title was false. Evidence: specs/container-deployment Host exposure bullet vs the scenario; design D7. Resolved: the requirement is REMOVED (Reason, Migration) and re-ADDED as "Compose topology publishes only the router, segmented, and operable", with the scenario renamed "Only the router publishes a host port" (proposal Capabilities, design D7).
- [x] [major] (failure) The `down` and `reset` targets did not pass `--remove-orphans`, so containers started by the other checkout (Realtime holds the superuser password) survive a reset and reach the fresh database that `compose run --rm migrate` creates before the next `up`. Evidence: `Makefile:69`, `Makefile:87`, `Makefile:66`; `docker ps` -> `autologger-dev-realtime-1 autologger-dev_db,...`. Resolved: every `compose down` step (dev/stage/prod down, both resets) gains `--remove-orphans` (design D5, spec "Makefile entry points" text and new scenario "A reset leaves no retired container running", task 4.1 checks nine steps).
- [x] [major] (failure, assumption) Rollback step 2 failed: the old generator and old `compose-run.mjs` refuse a partial trio, and `JWT_SECRET` stays. Evidence: `supabase-keys.mjs:113-115`; `compose-run.mjs:227`. Resolved: Rollback step 2 deletes `JWT_SECRET` too before running the old generator, and sets `SUPABASE_PORT` by hand (design Rollback).
- [x] [major] (failure, assumption) Rollback step 3 missed the two dropped `roles.sql` lines: on a database created after the change `authenticator` and `supabase_storage_admin` have no password, so reverted `rest`/`storage` can't log in and `supabase-gw` never starts. Evidence: image init `create user authenticator noinherit;`; `pg_hba.conf` scram for 172.16.0.0/12; `supabase-services.yaml:155-159`. Resolved: Rollback step 3 re-runs both `ALTER USER` lines with `make dev-psql` (design Rollback).
- [x] [major] (assumption) The Risks claim "GoTrue's admin API needs a service_role JWT … which only `auth` holds" was false: the retired `SERVICE_ROLE_KEY` (5-year expiry, signed with the kept `JWT_SECRET`) stays in OpenBao and the other checkout's containers, and the host reaches GoTrue's admin API directly. D6's "JWT_SECRET is rotated alone" also conflicted with owner decision 2. Evidence: `supabase-keys.mjs:38`; `compose-run.mjs:230-235`; host `curl http://172.28.35.2:9999/admin/users` -> `401`. Resolved: Risks states the residual (not new: the gateway gave the same reach with the same key) and orders the follow-up (remove the retired keys once no checkout runs the old stack, then rotate `JWT_SECRET`); D6 and tasks 5.1/5.2 put it in `docs/supabase.md` "Residual risks" and `docs/openbao-secrets.md` "Retired keys".
