# Panel: owner-bootstrap
Tier: 2 · Reviewers: assumption tester, failure and abuse, scope and simplicity · Date: 2026-10-02

No critical findings. Reviewers report only critical and major findings (ADR 0024).

- [x] [major] The owner's `GET /api/teams/:id` would omit `invites`: the gate at `teams.ts:190` is `role === 'admin'`, while the amended frozen row says `admin` or `owner`. No planned test caught it, because the fixture's `seedTeam()` adds the caller as `admin`. Found by the assumption tester and by scope and simplicity. Evidence: `sed -n 175,200p server/src/routers/teams.ts` -> `if (role === 'admin') { body.invites = …`. Resolved: D2 table and task 5.2 widen the gate to admin or owner; 5.1 adds "the owner's GET detail carries `invites`", plus a `teamDetailOwner` capture.
- [x] [major] Three delta scenarios had no named test: the owner renaming a former built-in plus the masked 404 for a non-member; `builtin: false` on the `studio` object of `POST /api/admin/studios`; the owner's promote, demote and remove sequence. Evidence: tasks.md 2.1 and 6.1 test only GET and `studios_catalog`. Resolved: tests named in tasks 2.1, 5.1 and 6.1.
- [x] [major] The design's open questions OQ1 (`enabled_admin_count` meaning), OQ3 (the support plane can leave a team ownerless) and OQ5 (transfer status codes) were written into the frozen-contract delta as settled before the owner decided them. Evidence: design.md OQ1/OQ5; the delta's `enabled_admin_count` row. Resolved: (owner, 2026-10-02) `enabled_admin_count` keeps its meaning (enabled admins only; the owner is not counted, so a new team reports 0); the implicit owner strip on the support plane is refused (next item); transfer returns 200 `{ok:true}`, 400 for a disabled target, 404 for a non-member, and a self-transfer is a 200 no-op. Recorded in proposal.md and design.md; the open questions are removed.
- [x] [major] The bootstrap claim takes over teams that other users created on dev and stage after 5a. On stage that is `my-crew2` and `my-studio`, each with one admin, plus the empty `my-crew`. The bootstrap owner gains content access and delete rights, and the creators lose role changes and delete. Evidence: stage `psql` -> `my-crew2|admin`, `my-studio|admin`; design.md D1 "No statement assigns an owner". Resolved: (owner, 2026-10-02) the takeover is accepted and recorded in Risks; the claim logs each claimed team id; prod has no users at cutover.
- [x] [major] The bootstrap email match used JS `toLowerCase()`, which folds non-ASCII lookalikes: U+212A KELVIN SIGN lowercases to `k`, so a different address could match the bootstrap email. Evidence: `node -e '"Kalen@gmail.com".toLowerCase()==="kalen@gmail.com"'` -> `true`. Resolved: the claim requires an all-ASCII token email and compares ASCII-lowercased, trimmed strings; boot refuses a non-ASCII `BOOTSTRAP_OWNER_EMAIL`; unit tests are named.
- [x] [major] Nothing verifies the prod `BOOTSTRAP_OWNER_EMAIL` before the first sign-in. A typo that is still a real address would hand every prod team to a stranger, and that can't be undone. Evidence: design.md D8 "No email-shape check"; the After-merge prod notes have no verification probe. Resolved: boot logs a masked form (domain plus a short hash, never the local part), with a unit test; the proposal's After-merge cutover notes verify the owner of `test-studios` right after the first prod sign-in.
- [x] [major] The support-plane upsert defaults a missing `role` to `member` (`admin.ts:94`). A routine re-POST against the owner would silently demote them, and the bootstrap claim would then take the team. Evidence: `admin.ts:94 body.role ?? 'member'`. Resolved: (owner, 2026-10-02) an upsert that would demote the current owner without an explicit `role` gets 409; an explicit role or a membership delete still works. This is in the api-contract-freeze delta with a scenario, a group 6 test, and Risks.
