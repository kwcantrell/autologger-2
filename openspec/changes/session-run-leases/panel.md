# Panel: session-run-leases
Tier: 2 · Reviewers: assumption tester, failure and abuse, scope and simplicity · Date: 2026-10-07

- [x] [critical] Putting the `ai-turn` claim in front of the process slot adds an `await` and a storage call inside the event-generation await-free window. That breaks core-ports-architecture ("no storage call or other `await` occurs before the per-session AI slot is acquired", spec.md:611-613) and `eventsGenerateWindow.test.ts:17-22`, which anchors on `aiChatTurns.tryAcquire(`. Raised by scope and assumption tester. Resolved: design D4 now takes the in-process slot first, synchronously and unchanged, then claims the lease. The window still ends at the literal `aiChatTurns.tryAcquire(`, and the source-anchor test is unchanged (task 5.1).
- [x] [major] Removing the in-process per-session sets lets one process run two turns for a session once its lease lapses (a strict renewal `UPDATE … expires_at_ms > now` can never recover after an outage of more than 40 s). Raised by failure and abuse, who suggested escalating it to the owner. Resolved: the registries stay unchanged in front of the lease (D4, D5), which is compatible with owner decision 1: per-session checks move to leases, process limits stay in memory. Renewal is now a re-claim by the same holder, so a lapsed row nobody took is re-taken (D2). Tested in 3.1 and 4.1. The owner is told explicitly at approval.
- [x] [major] The lease release was not awaited (`AiChatAcquireResult.release: () => void`, aiV2 `onFinally`, route `finally` blocks), so a response could end with the row still present and a follow-up could get `409`; a promise-returning release where `() => void` is expected trips `promiseHygiene.repo.test.ts`. Raised by all three reviewers. Resolved: D3 makes `release()` memoized and never-rejecting. D4 adds the `AiSlot` type with `release: () => Promise<void>`, awaited in every route `finally`. aiV2's `onFinally` gets `() => { void slot.release(); }` on the same memoized promise, so `RunDesignTurnOptions.release` stays `() => void`. Back-to-back tests are in 5.1, 5.2 and 5.3.
- [x] [major] The release order (process slot or lock first, lease second) opens a window in which a same-process request finds the slot free but the lease held, which changes the `409` details. Raised by assumption tester and failure and abuse. Resolved: D4 step 3 releases in reverse order (lease, then slot or lock), before the response completes. The spec delta requires it ("Released on every path, before the response").
- [x] [major] A transcript claim that throws leaks the process-wide lock, because the claim would sit between `tryAcquire` (generateTranscript.ts:86) and the `try` (:102). Raised by failure and abuse and assumption tester. Resolved: D4 opens the `try` before the claim, and a claim error releases the slot in every guard. Tested in 5.1, 5.2 and 5.3.
- [x] [major] D6's allowed test changes missed the ceiling-fill callers (`tryAcquire(other, 1)`) broken by the D5 signature change, and missed `eventsGenerateWindow.test.ts`. Raised by scope and assumption tester. Resolved: the registry signatures no longer change (D5), so those tests are unchanged. D6 now lists only two categories, and task 1.1 re-greps and classifies.
- [x] [major] Feature specs that would become false were not amended. transcript-generation requires the `409` to name the holding session when the requester may view it. topic-generation and ai-v2-dashboards attribute single-flight to the registry. Raised by scope. Resolved: a MODIFIED delta for transcript-generation "Single-flight generation" (a cross-process refusal gives the generic detail, with a new scenario). topic-generation and ai-v2-dashboards still hold as written, because the registry keeps its per-session check. The proposal's "Not changing" list is corrected.
- [x] [major] The ADDED scenarios "A long run keeps its lease" and "A crashed holder's slot frees by expiry" had no task that tests them as written. Raised by scope. Resolved: they are restated at the tested level (180 s with 18 renewals in `holdRunLease`; a takeover through process B in the store race test) and mapped to tasks 4.1 and 3.2(g). 5.2 also covers a route-level import after expiry.
