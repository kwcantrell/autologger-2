# Panel: companion-devices
Tier: 2 · Reviewers: assumption tester, failure and abuse, scope and simplicity · Date: 2026-10-08

- [x] [major] Another user could take over or delete a presence row by reusing its `client_id`, which isn't secret: it is the recording lease holder id that `GET /api/sessions/:id/status` returns to everyone with access to the session. The spec even said a post by another user "SHALL move the row", and `closing` deleted by `client_id` alone. Raised by the failure-and-abuse reviewer and the assumption tester. Evidence: `server/src/routers/events.ts:155` -> `audio_recording_lease_holder_id: lease.holder_client_id`; `web/src/api/hooks/useCompanionPresence.ts:66` and `AudioRecorder.tsx:391` share `getClientInstanceId()`; `server/src/routers/companion.ts:143-146` -> `presence.remove(cid)` with no user check. Resolved: rows are owned (design D3, D4). An upsert changes another user's row only once it is stale (15 s); `closing` and `remove` delete only the caller's own row; the POST still answers `200`. Tasks 3.1 and 5.1 add the tests.
- [x] [major] A blank-after-trim or NUL `client_id` passed validation and would hit the new table's check constraint, giving a 500 on a frozen route. Evidence: `packages/contract/src/schemas.ts:256` -> `client_id: z.string().min(1).max(256)`; `companion.ts:142` -> `body.client_id.trim()`, and `:150` checks NUL only in `session_id`. Resolved: both get `400` before any write (D3, task 5.1).
- [x] [major] A stolen or borrowed login cookie could mint device tokens that never expire, outlive logout, and that only the user can revoke. Evidence: design D5 (creation needs only the login gate); no TTL in D1 or D2; `server/src/routers/auth.ts:296-302` -> the cookie lasts `ttlDays`. Resolved: owner decision 8. Devices expire after 90 idle days and any use renews them; create, revoke and first use write audit log lines with user and device ids, never the token (D2, D5, tasks 4.1, 4.2, 6.1).
- [x] [major] An absent or empty `session_id` is stored as `''` today, which the new foreign key refuses, so every tab with no session open would get a 500. Raised by the scope reviewer and the assumption tester. Evidence: `companion.ts:153` -> `(body.session_id ?? '').trim()`; design D1 `session_id … references catalog.sessions(id)`. Resolved: absent, null or blank is stored as SQL `NULL` (D3, task 3.1).
- [x] [major] The proposal said cookie callers "keep today's view", but the design quietly filtered to accessible sessions and rescoped `connected_clients`. Evidence: proposal (before the fix) -> "A cookie caller keeps today's view"; base spec -> "resolve the active session as before (the freshest presence) and then check the caller's access … with `connected_clients` unchanged". Resolved: owner decision 9. A cookie caller uses only their own presence rows, the same rule as a device, and the proposal states the change (D3, the spec deltas).
- [x] [major] The device store's binding was undecided. The catalog facade has exactly five stores, so a `system()` facade couldn't host it, and the management routes had no stated binding. Evidence: `packages/catalog/src/catalog.ts:30-48` (five stores); `core-ports-architecture` "The `Catalog` type SHALL expose its domain stores (`shows`, `studios`, `auth`, `sessions`, `profile`)". Resolved: owner decision 10. One `CompanionDeviceStore` in storage on `bindSystem('companion-device')`, wired as `ports.companionDevices`. The table is system-only like `kv`, and every management statement is scoped by the caller's user id in SQL, which the integration tests pin (D1, D2, D5).
- [x] [major] D9's categories for changing existing tests missed tests the change must break. Raised by the scope reviewer and the assumption tester. Examples: bearer presence posts that now get 403 (`companion.int` closing, `nulText.int`); the `catalogPolicies.pg` user-policy count and `table !== 'kv'` rule; `catalogSchema.pg` `relname !== 'kv'`; `identity.test.ts` for the deleted `requestHasValidApiToken`; the `aiV2.int` "API_TOKEN is inert" block; `leaseSweeper.int`'s `sweepLeasesOnce` call; `companion-ws.int`; `_helpers.test.ts` `apiTokenAuth`; and the `SettingsView.test.tsx` tab list. Evidence: `grep -rn "toBe(t.relname !== 'kv')\|toHaveLength(37)" server/src/test/pg` -> both hit. Resolved: D9 categories 7-12 cover each one, and the task 1.1 grep is widened to find them.
- [x] [major] The presence step in the sweeper had no sweeper-level test, its position was unspecified (the tick returns early when the recording listing fails), and the port contract didn't list the method. Evidence: `server/src/startupPurge.ts:75-80` -> `return;` on a listing failure. Resolved: the step runs first and is warn-only. The port lists `deleteOlderThan`, and task 3.1 adds `startupPurge.test.ts` cases (D4).
- [x] [major] The presence freshness boundary changed from inclusive to exclusive without saying so, while D9 said the pg tests copy the same cases. Evidence: `server/src/node/presence.test.ts:61-63` -> "exactly at the window edge is still fresh". Resolved: `list` is inclusive at the 15 s edge, as today (D4, task 3.1).
- [x] [major] The web-ui-system delta added the Settings section but left the existing exhaustive section list unchanged, so the specs contradicted each other. Evidence: `openspec/specs/web-ui-system/spec.md:331-335` -> "**You:** Account." Resolved: a MODIFIED "Settings modal defers inactive tab content" adds Companion devices to the You group.
- [x] [major] Stale `API_TOKEN` and presence references were left outside D8 and task 9.1. Evidence: `docs/supabase.md:98` -> "needs `API_TOKEN` too"; the `compose.yaml:87` comment; `web/src/api/hooks/useCompanionPresence.ts:8` cites `server/src/node/presence.ts`; `packages/ai-runtime/src/aiV2PendingQuestions.ts:73-77`; the `fakeClock.ts` comments.
