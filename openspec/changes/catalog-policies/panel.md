# Panel: catalog-policies
Tier: 2 · Reviewers: assumption tester, failure and abuse, scope and simplicity · Date: 2026-10-03

Reviewers report only critical and major findings (ADR 0024).

- [x] [critical] The scenario "Unrelated teams don't serialize against each other" and the D10/4.1 cross-team test cannot hold. Two owners of different teams, interleaved (own membership `FOR SHARE`, session update, show insert, invite insert), always abort one transaction with 40001. On small tables the session update's `accessible_shows` takes a page lock on the single-leaf `idx_shows_studio`, which the other team's show insert writes into; D10's fallback reads the same index. Once tables are analyzed, 6b-1's allow-all shows the same failure, so the cause is SERIALIZABLE on small tables, not the policies. Evidence: `STEPS=0123 node xteam.mjs r owner` -> allow-all `"2":"1,1,1,1,COMMIT"`, policies `"2":"1,1,1,1,FAIL40001"` (3×); `STEPS=12` -> `FAIL40001`; locks `page:idx_shows_studio:1 page:shows:0`. Resolved: (owner, 2026-10-03) cross-team conflicts are accepted and absorbed by the adapter's retries. The scenario says they never surface at HTTP within the retry budget, and the cross-team test asserts that both transactions commit through the retry loop. Stop rule: stop and ask if the 40001 retry rate more than doubles versus 6b-1, measured on analyzed test databases, or if any request exhausts its retries.
- [x] [major] The lock-granularity test, the retry baseline and the probe only hold on unanalyzed test clones. With statistics, the app's own SQL picks sequential scans and takes relation-level SIRead locks; dev already has `shows` analyzed. Evidence: on an analyzed db, `update catalog.sessions … where id='ss1'` as g -> `relation|sessions|1`; same as `catalog_system` -> `relation|sessions|1`. Resolved: the design states that clones have no statistics, the contention tests and the retry and probe measurements also run after `ANALYZE`, and the vacuous granularity test is rewritten.
- [x] [major] The `users` write rule (`id = me`) had no column limit. A future bug in a user-bound path could let users set their own `email` and hijack invites to other teams, change `google_sub` or `disabled_at_utc`, or delete their own row (the cascade leaves the team with no owner). Evidence: `authStore.ts:561-563` matches invites on stored email; `teams.ts:242-247`; design D2 `users` row. Resolved: `catalog_user` gets column-level UPDATE on the name columns only, and no INSERT or DELETE. The matrix tests refused email, `google_sub` and `disabled_at_utc` updates and a refused delete.
- [x] [major] The team-management rules checked only the team, so behind an app-gate bug a plain member could insert a membership for any user id into their team (exposing that user's row through `co_members`), raise their own role, or add invites. Evidence: design D2 rows; `co_members` reads memberships; proposal owner decision 1 "holds the team boundary". Resolved: (owner, 2026-10-03) `catalog_user` has no INSERT on memberships or invites; only the system reasons add them. The partial unique owner index already blocks self-promotion to owner while the team has one. The remaining within-team escalations (raising one's own role to admin; deleting members, grants or invites) are recorded in Risks as covered only by the app's in-transaction gates.
- [x] [major] The race-only outcomes in D8 change frozen behaviour without an `api-contract-freeze` delta; for example, `PUT /api/sessions/:id` racing a revoke goes from 200-and-write to 404-and-no-write. Evidence: `api-contract-freeze/spec.md:16-23`; the precedent at `:1474` ("This narrows … only for this race"); `design.md:365-367`. Resolved: an ADDED `api-contract-freeze` requirement lists these race outcomes, and the proposal no longer claims no status changes.
- [x] [major] `PUT /api/profile` racing a demotion would answer `403 Admin role required.` after earlier settings writes had committed, but the frozen contract pairs that 403 with "nothing SHALL be written". Evidence: delta `core-ports-architecture/spec.md:23-25` "Writes it made before that point stay"; `api-contract-freeze/spec.md:1555-1558`. Resolved: the route re-checks the role with `FOR SHARE` inside the transaction before its first write, so a demotion yields the 403 with nothing written; a race test is added.
