# Panel: show-grants
Tier: 2 · Reviewers: assumption tester, failure and abuse, scope and simplicity · Date: 2026-10-02

Reviewers report only critical and major findings (ADR 0024).

- [x] [critical] Any signed-in user can drive the session the Companion targets. `state`, `log`, `transport`, `command` and `categories` act on the freshest presence across the whole process and never check the cookie caller. An ungranted member, or a user in another team, can read its state and categories, write events, start and stop takes, and broadcast record and stop commands. The delta pinned this as "no per-caller access check". Found by failure and abuse, and by the assumption tester. Evidence: `server/src/routers/companion.ts:86-97` `primarySession(await c.env.ports.presence.list())` with no user check; `server/src/middleware/auth.ts:30-42` a cookie user passes on `/api/companion/*`. Resolved: when a cookie user is present, those five routes check `canAccessSession` on the resolved session and deny exactly as when no session is active. Token-only callers stay the system caller (owner decision 6). The delta is reworded; the routes join the D15 route-table test, with int tests.
- [x] [major] A revoke, a removal or a demotion never reaches an already-open session WebSocket. The user keeps receiving pushes and can send record and stop commands for the life of the socket. Evidence: `server/src/routers/sessionWs.ts:12-27` gates only before the upgrade; `packages/session-core/src/SessionHub.ts:393-405` broadcasts `command` with no principal. Resolved: (owner, 2026-10-02) the hub records the user per socket, and revoke, remove and demote close that user's sockets on the affected sessions after commit; spec scenarios and tests added. Follow-up for slices 8 and 9: drive this from the database (row trigger and `pg_notify`, or Realtime policies).
- [x] [major] Log-import and YouTube-import jobs check access once, then keep writing after a revoke. Evidence: `server/src/routers/logImport.ts:156-205` is a detached job with no re-check; `sessions.ts:365,433`. Resolved: (owner, 2026-10-02) each job re-checks the creator's show access before each step, and on loss stops with an "Access revoked" line; already-written events stay. Spec and tests added.
- [x] [major] The session list gives an ungranted member free-text `notes`, live recording state and event counts for every show in their team, not just titles. Evidence: `server/src/routers/sessions.ts:89-99`; `profile.ts:107-115` (`active_show_id` needs only team membership). Resolved: (owner, 2026-10-02) the JSON shape is unchanged, but content and live-state fields are blanked for a caller without access to that show, so only titles and dates remain. Contract delta and tests added.
- [x] [major] The `transcript-generation` capability restates the lock-redaction membership rule that D12 changes, and it had no delta, so two live specs would contradict each other after archive. The 409 in-flight case had no test for an ungranted member. Found by scope and simplicity, and by the assumption tester. Evidence: `openspec/specs/transcript-generation/spec.md:47-51,64-67,86-89,107-110` "a member of the holder's studio". Resolved: MODIFIED deltas restate those requirements in terms of show access; a 409 test for an ungranted member is added.
- [x] [major] `sheets-log-import` "Job authorization and lifecycle" names only non-members as the 404 case, and its 200 scenario says any studio member. Other specs' "member" scenarios (`topic-generation:254`, `auto-event-generation:483`, `local-container-environments:168`) were not reviewed. Evidence: `openspec/specs/sheets-log-import/spec.md:111-113,176-178`. Resolved: a MODIFIED delta for sheets-log-import; D16 records which of the other scenarios stay literally true.
- [x] [major] The `GET /api/teams/:id/shows/:showId/grants` list route has no consumer, because the web reads `members[].show_ids`. Adding it would freeze audit fields and an always-true `can_write` on the wire. Evidence: design.md D5 vs D13 (`useSetShowGrant` issues only PUT and DELETE). Resolved: (owner, 2026-10-02) cut, together with its fixture, tests and README row; PUT and DELETE stay.
- [x] [major] `can_access` on `GET /api/shows`, `GET /api/shows/:showId` and `POST /api/shows` is justified only by a compiler assignability check; the web reads access from the profile. Evidence: design.md D7 and OQ6; `web/src/api/types.ts:118-120`. Resolved: (owner, 2026-10-02) `can_access` appears on profile `shows[]` only, typed as `ProfileShow`.

## Consistency read 2026-10-02

Scope change: no
- [x] [major] Closing sockets after access loss failed open, and its callers read the team's show ids outside its try. A database error after a committed revoke, removal, leave or demotion left the user's sockets open (the spec says SHALL close), or returned 500 for a write that had already committed. Evidence: `server/src/routers/_helpers.ts` `closeSocketsAfterAccessLoss` caught and logged only; `teams.ts:345,369,388` and `admin.ts:116,130` passed `await teamShowIds(...)` as an argument. Resolved: the show ids are read lazily inside the try, and any failure closes every socket of the user (`closeUserSockets(userId, 'all', 4403)`); a socket that still has access reconnects through the gate. Unit tests cover both failure points; session-core covers `'all'`; the socket, teams and admin int suites pass.
