# web-docs-site

## Purpose

Drift-gated architecture atlas workspace: a static `web-docs/` site that documents the
repo's own architecture and stays honest by construction. Governs the component model
mapping every tracked source file to exactly one component; the derived cross-component
edge extraction, classification, and committed-snapshot drift gate; mechanical evidence
rules for declared non-import relationships; capability accounting against the
`openspec/specs/` baseline with pending-grace for capabilities named only by an active
change's delta specs; mermaid diagram validity (DOM-bootstrapped parsing, size budgets,
dangling-navigation checks) and injection-safety (strict mode, escaped disk-derived
strings); the three-level drill-down site (L0 system diagram, L1 per-component module
graphs, L2 ER/state diagrams and the requirement browser); and deterministic, offline,
git-ignored-artifact-free builds. Established by the `web-docs-architecture-viz` change
(archived 2026-08-07).

## Requirements

### Requirement: web-docs is a static workspace with zero server involvement

The repo SHALL contain a `web-docs/` npm workspace whose build produces a fully static
site (HTML/JS/CSS + a generated `atlas.json`), served locally by its own dev server. The
build and the site SHALL NOT modify, depend on a running instance of, or add any route,
JSON shape, or WS message to the server — the frozen HTTP/WS contract is untouched. The
dev server SHALL bind loopback only, on a port that does not collide with 5173/8787/8791.
`atlas.json` SHALL be a git-ignored artifact regenerated by every build and dev-server
start, never committed.

#### Scenario: Static build with no server changes
- **WHEN** `npm run build -w web-docs` completes on a clean checkout
- **THEN** a static site exists under `web-docs/dist/`, and no file under `server/src`, `web/src`, or `companion/src` has been modified

#### Scenario: Root chains include web-docs
- **WHEN** root `npm run typecheck`, `npm test`, or `npm run lint` runs
- **THEN** each includes a `web-docs` leg (the `test` leg running the workspace's unit tests), and root `dev`/`build`/`start` remain unchanged

### Requirement: Live-repo drift gates run at build and via docs:check

The extraction pipeline and every drift gate in this spec SHALL execute against the live
working tree in exactly two entry points: `npm run build -w web-docs` and a root
`npm run docs:check` script. Root `npm test` SHALL NOT run the live-repo gates (it runs
the workspace's fixture-based unit tests only). When the gates run, a violation SHALL be
a hard error (non-zero exit): gates SHALL NOT be downgraded to warnings, satisfied from
cached extraction results, or bypassed by per-file exemptions beyond the explicit
exclusion list defined below. No component glob may be a bare workspace source root
(e.g. `server/src/**` as a single component).

#### Scenario: docs:check runs all gates against the live tree
- **WHEN** root `npm run docs:check` runs
- **THEN** extraction and every drift gate execute against the current working tree, exiting non-zero on any violation

#### Scenario: Gate failures are errors, not warnings
- **WHEN** any drift gate detects a violation during build or docs:check
- **THEN** the process exits non-zero; no configuration exists to demote the violation to a warning

### Requirement: Component model maps every tracked source file to exactly one component

`web-docs/model/components.ts` SHALL define the component model: named components with a
`kind` (`runtime` | `datastore` | `external` | `tooling` | `test-harness`), description,
source globs, attached OpenSpec capabilities, and attached authored diagrams, plus
declared non-import relationships. The coverage gate SHALL enumerate tracked `.ts`/`.tsx`
files from git (not from a hand-listed root set) and fail when any tracked file matches
zero components or more than one component, unless the file appears on an explicit,
model-declared exclusion list that the site renders on its About page. Per-module test
files map to the same component as the code they test; shared harness directories (e.g.
`server/src/test/`) form `test-harness` components.

#### Scenario: Orphan tracked file fails
- **WHEN** a tracked `.ts`/`.tsx` file matches no component's globs and is not on the exclusion list
- **THEN** the gate exits non-zero naming the file and the nearest matching component

#### Scenario: Overlapping globs fail
- **WHEN** a tracked file matches the globs of two components
- **THEN** the gate exits non-zero naming the file and both components

#### Scenario: Exclusions are visible, not silent
- **WHEN** the site renders its About page
- **THEN** every excluded file is listed with the model's stated reason

### Requirement: Cross-component edges are derived, classified, and checked against a reviewed snapshot

The extraction step SHALL resolve import/export declarations (including literal dynamic
`import()`) of every mapped file via the TypeScript compiler API — building its program
from the mapped-file list itself and using each workspace's `compilerOptions` for module
resolution only (never each tsconfig's `include`/`exclude`), covering all four resolution
regimes (server, web with its `paths` aliases, companion's NodeNext `.js`-specifiers,
e2e). Unresolvable non-TypeScript specifiers (CSS, images, bundler-only assets) SHALL be
ignored; non-literal dynamic imports SHALL be reported as warnings with call sites; an
import resolving to an in-repo file that belongs to no component and is not excluded
SHALL fail the gate naming both files. Each derived component-level edge SHALL be
classified `production` or `test` (an edge is `test` when every underlying import
originates in a test file or a `test-harness` component). The derived, classified edge
set SHALL be compared to a committed snapshot (`web-docs/model/edges.snapshot.json`):
any difference — a new edge or a vanished edge — SHALL fail the gate, naming the edge,
the underlying file imports, and the regeneration command, so architectural drift is
reviewed in the diff that causes it.

#### Scenario: New observed edge fails until snapshot is re-reviewed
- **WHEN** a file in component A gains an import into component B and no A→B edge of that kind exists in the committed snapshot
- **THEN** build/docs:check exits non-zero naming the importing file, the imported file, and the snapshot-regeneration command

#### Scenario: Vanished edge fails until snapshot is re-reviewed
- **WHEN** the snapshot contains an A→B edge and extraction observes no underlying import
- **THEN** build/docs:check exits non-zero naming the stale edge

#### Scenario: Import into unmapped in-repo file fails
- **WHEN** a mapped file imports an in-repo `.ts` file that belongs to no component and is not on the exclusion list
- **THEN** the gate exits non-zero naming the importing and imported files

### Requirement: Declared non-import relationships carry mechanical evidence

Cross-process and non-import relationships SHALL be declared in the model with a named
evidence rule the gate checks mechanically — at minimum: web→server HTTP/WS (evidence:
the web API client module exists and contains `fetch`/WebSocket call sites),
companion→server HTTP (evidence: the companion API client module exists and contains
`fetch` against its configured base URL), server→web static-serve (evidence: the
`serveStatic` call site), e2e→server/web/companion process-spawn (evidence: the harness
spawn call sites), and server→datastore/external edges (catalog DB, session DBs, blob
store, DeepGram, Claude CLI, yt-dlp, Google JWKS; evidence: the owning module's call
site, with config-gated externals labeled as gated). A declared relationship whose
evidence check fails SHALL fail the gate. Relationships SHALL render distinctly from
import edges, and the site SHALL label their verification as call-site-level (not
per-endpoint).

#### Scenario: Unevidenced relationship fails
- **WHEN** the model declares a relationship whose evidence rule finds no match
- **THEN** the gate exits non-zero naming the relationship and its evidence rule

#### Scenario: External services appear with their gates
- **WHEN** the L0 diagram renders
- **THEN** DeepGram, Claude CLI, yt-dlp, and Google JWKS appear as `external` nodes labeled with their configuration gates, distinct from import edges

### Requirement: Baseline capabilities map to components; new capabilities get pending-grace

Every capability directory under `openspec/specs/` SHALL be accounted for in the model as
exactly one of: attached to ≥1 component; declared `cross-cutting` with an explicit
component set; or declared `process` (attached to no component, listed on the About
page). An unaccounted-for baseline capability SHALL fail the gate naming it; a model
reference to a capability that exists neither under `openspec/specs/` nor as an active
change's delta capability SHALL fail the gate. A capability named only by an active
change's delta specs (not yet archived to the baseline) SHALL be rendered as a visible
"pending" capability and SHALL NOT fail the gate.

#### Scenario: Unaccounted baseline capability fails
- **WHEN** `openspec/specs/` contains a capability the model neither attaches nor declares cross-cutting/process
- **THEN** the gate exits non-zero naming the capability

#### Scenario: New capability from an active change is pending, not fatal
- **WHEN** an active change's delta specs name a capability absent from `openspec/specs/`
- **THEN** the site lists it as pending and the gate passes

### Requirement: Three-level drill-down site

The site SHALL render: (L0) a system architecture diagram of all components — nodes
carrying their model `kind`, with `runtime`/`datastore`/`external` nodes shown by default
and `tooling`/`test-harness` nodes behind a toggle — drawing every `production` edge from
the snapshot plus declared relationships, with `test` edges behind a toggle, each node
navigating to its component page; (L1) a page per component showing its internal module
graph from observed imports, where every mapped file appears as a node or inside a named
subdirectory group, test files are elided by default with the elided count displayed and
a toggle to show them; plus the component's attached capabilities with requirement
counts, and active changes touching it; (L2) detail views — ER diagrams, authored state
diagrams, and the requirement/scenario browser. A renderer assertion SHALL verify the L0
mermaid source contains every snapshot `production` edge and declared relationship.

#### Scenario: L0 node navigates to component page
- **WHEN** a user activates a component node on the L0 diagram
- **THEN** the site navigates to that component's L1 page

#### Scenario: L0 cannot silently elide edges
- **WHEN** the L0 mermaid source is generated
- **THEN** a build-time assertion verifies it contains every `production` edge in the snapshot and every declared relationship, failing otherwise

#### Scenario: L1 accounts for every mapped file
- **WHEN** a component's L1 page renders
- **THEN** every mapped file of that component appears as a node or inside a named group, and the count of elided test files is displayed

### Requirement: Mermaid runs strict; navigation and text are injection-safe

Client-side mermaid SHALL run with `securityLevel: 'strict'` and `htmlLabels: false`;
node navigation SHALL be implemented by post-render DOM handlers mapping node ids to
routes (not mermaid `click` directives); every disk-derived string (component names,
file paths, capability names, change names, spec text) SHALL be escaped for mermaid
label syntax before interpolation; and requirement/spec text SHALL be rendered as text
nodes, never as HTML.

#### Scenario: Hostile spec heading cannot execute
- **WHEN** a spec heading or change directory name contains HTML/script-like content
- **THEN** it renders inert as escaped text in diagrams and browser pages alike

### Requirement: ER diagrams are produced by schema introspection

The extraction step SHALL construct the catalog schema by executing the real migration
files in order against a bare in-memory SQLite database, and the session-DB schema by
initializing it via the server's exported `SessionCore` — constructed over a second
in-memory handle with the exported `sqliteSessionSql` adapter and inert runtime stubs,
then calling `initSchema()` — and introspect tables, columns, primary/foreign keys and
emit mermaid `erDiagram` sources. DDL text SHALL NOT be parsed directly. SQLite-internal
objects (`sqlite_%`) and the migrator's own `_migrations` bookkeeping table SHALL be
excluded; only schema (never row data) SHALL be captured.

#### Scenario: Catalog ER reflects migrated schema
- **WHEN** extraction runs against the current migrations
- **THEN** the catalog ER diagram contains every non-internal table and column present in the migrated in-memory database, including declared foreign-key relationships, and excludes `sqlite_%` and `_migrations`

#### Scenario: Session ER reflects initSchema
- **WHEN** extraction runs
- **THEN** the session ER diagram contains every table and column the session `initSchema` creates

#### Scenario: New migration is reflected without web-docs edits
- **WHEN** a future migration adds a table and extraction re-runs
- **THEN** the new table appears in the ER diagram with no change to web-docs sources

### Requirement: Authored state diagrams are attached, structurally validated, and labeled

Authored mermaid `stateDiagram-v2` sources SHALL live in `web-docs/diagrams/`, be
attached to components via the model, and be labeled "authored" in the UI (distinct from
mechanical diagrams). v1 SHALL ship exactly two, derived from a read of the current code:
the recording-lease lifecycle (including stale-holder takeover and alarm re-arm) and the
SessionHub registry lifecycle (construct → active → evict-and-reconstruct, with the
idle-eviction guards). The transcript-generation flow SHALL NOT be authored in v1 (it is
under concurrent revision by the `transcript-gen-lock-status` change). The gate SHALL
fail if an attached diagram file is missing, fails mermaid parsing, or is structurally
empty (no states or no transitions).

#### Scenario: Broken or empty authored diagram fails
- **WHEN** an attached state-diagram file is absent, unparseable, or contains no states or no transitions
- **THEN** build/docs:check exits non-zero naming the file

### Requirement: Diagram validity gates use a DOM-bootstrapped parser and size budgets

Build-time mermaid validation SHALL run with a DOM shim (jsdom or equivalent) bootstrapped
before mermaid loads — never a dependency that downloads a browser at install (puppeteer /
`@mermaid-js/mermaid-cli` are prohibited). Beyond parsing, every generated diagram SHALL
pass structural checks: non-empty node set, every navigation id resolving to a real
component route, and per-diagram size budgets (maximum node and edge counts) enforced as
hard failures so grouping thresholds are proven adequate rather than assumed. The client
SHALL initialize mermaid with the same configuration object carried in `atlas.json` that
validation used.

#### Scenario: Dangling navigation id fails
- **WHEN** a generated diagram carries a navigation id with no corresponding component route
- **THEN** build/docs:check exits non-zero naming the id

#### Scenario: Oversized diagram fails
- **WHEN** a generated diagram exceeds its node or edge budget
- **THEN** build/docs:check exits non-zero naming the diagram and the exceeded budget

### Requirement: Requirement browser is parsed from spec markdown with a count gate

The extraction step SHALL parse each `openspec/specs/*/spec.md` into a capability →
requirements → scenarios tree from its `### Requirement:` / `#### Scenario:` headings,
and the site SHALL render it navigably from each component's capability list, as text.
The parsed requirement and scenario counts per capability SHALL equal a direct heading
count of the file; any `### `/`#### ` heading inside a Requirements section that the
parser cannot classify SHALL fail the gate.

#### Scenario: Requirements render for a capability
- **WHEN** a user opens a capability from a component page
- **THEN** its requirements and their scenarios are shown, matching the headings on disk

#### Scenario: Parser cannot silently drop a requirement
- **WHEN** the parsed count for a capability differs from the file's direct heading count
- **THEN** build/docs:check exits non-zero naming the capability

### Requirement: Active changes overlay from tracked artifacts

The extraction step SHALL enumerate active changes from git-tracked files under
`openspec/changes/` (excluding `archive/`): a change is a directory containing a tracked
`proposal.md`; directories without one contribute nothing and produce a build warning.
Each change's touched capabilities come from its delta-spec capability directories:
component-scoped capabilities tint their components on L0/L1 with links to the change's
proposal; cross-cutting capabilities are listed on the change without tinting;
delta-less changes are listed without tinting. Pending (new) capabilities render per the
pending-grace requirement.

#### Scenario: Change tints its components
- **WHEN** an active change contains a delta spec for a component-scoped capability attached to component C
- **THEN** the L0 diagram tints C and links it to that change

#### Scenario: Cross-cutting deltas do not flood the map
- **WHEN** an active change's delta names a cross-cutting capability
- **THEN** the change lists the capability but no component is tinted by it

#### Scenario: Untracked or partial change directories are inert
- **WHEN** a directory under `openspec/changes/` has no tracked `proposal.md`
- **THEN** it contributes nothing to the overlay and a warning names it

#### Scenario: Archived changes are excluded
- **WHEN** a change directory lives under `openspec/changes/archive/`
- **THEN** it contributes nothing to the overlay or the change list

### Requirement: Builds are deterministic and offline

The extraction step and site build SHALL be deterministic: all collection iteration
sorted, all paths repo-relative, and `atlas.json` SHALL contain no absolute paths or
hostnames, so identical inputs produce byte-identical `atlas.json` across machines. The
build SHALL perform no network access, SHALL NOT invoke any LLM, and SHALL NOT read
git-ignored artifacts (`.codegraph/`, `openspec/changes/**/.apply/`, `DATA_DIR` contents,
test output dirs) — `node_modules` and the tracked tree are its only inputs.

#### Scenario: Two runs are byte-identical with no gitignored reads
- **WHEN** extraction runs twice on the same commit
- **THEN** both runs produce byte-identical `atlas.json`, and no read touches `.codegraph/` or other git-ignored artifacts

#### Scenario: Atlas carries no machine-specific paths
- **WHEN** `atlas.json` is inspected
- **THEN** it contains no absolute filesystem paths and no hostnames
